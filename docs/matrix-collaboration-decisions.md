# Matrix 协作：决策登记册

日期：2026-09-25。状态：**讨论项登记，未实现**。

用途：把"什么是已定、什么是开放、什么已被否决"分开记，避免在后续轮次里被重新提案或被
当成已实现。实现契约与验收门禁在 [`matrix-pod-storage-portability.md`](matrix-pod-storage-portability.md)；
本文只登记决策与其依据。

规则：

- **已定**：有依据、不再重开；要改必须给出新证据并显式修订本文。
- **开放**：尚未拍板，实现前必须先定；不得用实现细节代替拍板。
- **已否决**：曾被提出并因具体理由否决，附否决依据，避免反复。

## 一、产品与协议边界

| # | 事项 | 状态 | 依据 |
| --- | --- | --- | --- |
| 1 | Matrix 只是**兼容入口**，产品本体是"共享 Pod 聊天模型" | 已定 | 设计文档产品边界 |
| 2 | 消息形状遵守 **Solid Chat 词表**，不区分群聊/私聊、不区分 app 或协议 | 已定 | 见 §二.1 |
| 3 | 协作半径 = **同一个共享 Pod** 内的多身份；房间事实只存在这一个 Pod | 已定 | V1 边界；设计文档明确无 federation |
| 4 | 每个参与者各自 Pod 各存一份副本（跨 Pod 分发） | **超出范围** | 与 3 冲突，需单独立项 |
| 5 | 端侧同步所需状态必须能**从 Pod 求出**；API 只负责按协议形状读写 | 已定 | 见 §二.2 |
| 6 | E2EE、完整 power levels、Matrix 原生登录、federation | 超出范围 | 设计文档已声明 |

## 二、逐条决策

### 二.1 消息形状与身份

**已定**

- 消息谓词来自 Solid Chat：`wf:message`（chat←message 反向）、`sioc:has_member`
  （thread←message 反向）、`sioc:has_parent`、`foaf:maker`、`sioc:content`、
  `sioc:richContent`。群聊与私聊、Matrix 与其它 app 的差别只在**取值**
  （`foaf:maker` 是 WebID / agent URI / contact URI）与 `metadata`。
- **不得**为 Matrix 的某个机制改消息布局、日期分桶或加协议分支。若某个需求要求
  "区分是不是群聊 / 是不是首条消息"，说明该机制放错了层。
- 消息文档保持 `/.data/{parent.dir}/{yyyy}/{MM}/{dd}/messages.ttl#{id}`；同房间同日共用
  一个文档。
- **身份以 message URI 为准**；`event_id` 是它的确定性投影：
  `event_id = '$' + hash(canonical message URI)`。保留 `$` 前缀，因为 Matrix 客户端按它
  校验并使用 event_id；直接把 URI 当 event_id 属于协议面不兼容。

**开放**

- 是否进一步让 `event_id` 直接等于 Solid URI（更"原生"，但要接受非 Matrix 形状的
  event_id，需确认目标客户端容忍度）。

### 二.2 端侧同步状态的归属

**已定**

- 判据：**换一个部署实例、清空本地派生状态后，仅凭该 Pod 能否继续为同一客户端提供正确的
  增量同步与重放语义？** 不能，则说明同步状态放在了错误的层。
- 因此游标位置必须**从 Pod 内容可求**，不能是部署侧分配的单调序号；`txnId` 去重回执必须
  是 Pod 内**可按事务键寻址**的记录。
- 客户端只保存并回传不透明 token；服务端不应是端侧同步状态的唯一持有者。

**开放**

- 游标 token 的具体形态与压缩策略（候选：已见事件引用集合 / 有界位置 / 其它）。
- 是否需要"全局单调序号"：规范只要求 token **不透明且不漏事件**，`v2_<seq>` 是自选形状。
  若不需要，发布日志（分段 + 开页 CAS）可整体省去。

### 二.3 去重与重放

**已定**

- 消息追加本身已幂等：ORM 写入为 `INSERT DATA`，RDF 集合语义下同一组 triple 重放无副作用。
  **不需要"这条消息是否已存在"的判断。**
- `txnId` 幂等需要的是"按 txnId 找回**首次**签发的结果并原样返回"，载体是一个可按事务键
  寻址的记录资源（候选一），与消息资源无关。
- 同 txnId 重放必须返回原响应（含原 event_id）；内容不同按冲突契约返回 409，不覆盖首次接受。

**开放**

- 事务记录资源内"可恢复载荷"的保留期限与回收策略。
- 事务键的完整构成（至少含 scope、身份/设备、完整端点作用域与版本域）与编码方式。

### 二.4 授权

**已定**

- Pod 访问是 **caller-owned**：用调用者自己的凭据，CSS 只校验用户权限；不借用 owner 存量密钥。
- 跨请求授权判定缓存属**新鲜度放宽**，必须显式记录，不得表述为等价优化。
- 执行提交路径（agent wake claim/complete）**必须新鲜判定**；已通过
  `x-xpod-authorization-fresh` 内部标记落地。

**开放**

- 可接受的撤权语义：普通 ACL/ACR 写入不经 SPARQL 处理器，TTL 内的旧 allow 命中是否可接受，
  需要产品侧拍板；跨实例失效机制不在当前范围内。

### 二.5 执行与恢复

**已定**

- 执行来源证明必须有**独立于同步日志**的持久载体；普通消息 metadata、确定性 ID、
  资源存在性**不能**充当证明。
- 执行语义是**至少一次**；外部工具需自带幂等。

**开放**

- 证明机制选型（仅受信服务可写的证明资源 / 可验证签名记录）及其密钥模型、轮换与历史验证。

## 三、已否决（附依据，勿重复提案）

| 提案 | 否决依据 |
| --- | --- |
| 用 `If-None-Match: *` 判定"单条消息首次插入" | 条件头只保护整个 HTTP 文档，而同房间同日消息共用一个文档；且它解决的是一个**不存在的问题**（消息追加本就幂等） |
| 改 models 的日期分桶/布局以便逐消息条件创建 | 违反 §二.1 的 Solid Chat 遵守原则 |
| 用 scope 级行锁优化 `xpod_matrix_events` 表锁 | 那是在优化一个自造的全局分配器；正确方向是让游标从 Pod 可求（§二.2） |
| 保留 SQL journal 作为游标/回执的长期权威 | 与 §二.2 判据冲突：新部署实例无法为同一客户端续接同步 |
| 把去重/游标放到 provider 私有结构或依赖某后端特性 | 违反"支持所有 CSS provider"的可移植性决定 |
| 跨 Pod 复制房间事实（每个参与者一份） | 超出 V1 边界（§一.3），需单独立项 |

## 四、开放项汇总（实现前必须先定）

| # | 开放项 | 阻塞什么 |
| --- | --- | --- |
| 1 | 游标 token 形态与是否需要全局单调序号 | 决定发布日志是否存在，是后续一切同步实现的前提 |
| 2 | 事务记录资源的构成、载荷保留与回收 | 去重与崩溃恢复的实现 |
| 3 | 两个新资源是否必须在 `@undefineds.co/models` 定义 | 跨仓库命名与布局 |
| 4 | 可接受的撤权语义 | 授权缓存能否留在读路径以外 |
| 5 | 执行来源证明机制 | 可信执行触发 |
| 6 | 甲/乙边界是否延伸到跨 Pod 副本 | 房间事实的存储拓扑 |
