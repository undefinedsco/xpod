# Xpod case：Symphony 联合验收测试样例

状态：样例规格，未实现自动化、未执行。对应 [验收计划](symphony-decision-acceptance.md)，编号与该计划一一对应。下面的名称是测试标签，不定义新的共享 schema。

## 固定初始状态

主执行宿主为 DSH。每例除 Xpod 请求和 Git 证据外，还需关联 DSH session/任务与实际加载的 Symphony 版本。先通过 [宿主预检](symphony-decision-acceptance.md)，再执行场景；DSH 缺能力应记 blocked，不切到 Codex 执行后算作 DSH 通过。

每个独立用例从自己的基线开始，不能默认承接上一行的变更。连续故事例外，必须保留同一条证据链。

- 用实际 Xpod 测试账号 U、Pod P 和受控验收仓库。禁止使用真实业务修改充当故障夹具。
- Xpod case A：验证新增 provider 的能力声明；owner A 在 worktree A，基线提交 B0，需求文档 rev1，状态 running。验收要求：声明真实、未知协议不误路由、凭据不泄露。
- 独立 case B：验证连接配置读回；owner B 在 worktree B，同样跟踪目标分支 B0。A、B 都是 Xpod 用例，不是 LinX 功能。
- 兼容变更 rev2：“补一条未知协议不能手动选择模型的验收”，保持原目标和接口。
- 失效纠正 rev3：“取消全部模型默认 Chat 的假设，缺协议必须明确不可调用”，用于刻意保留了旧假设的执行样例。
- 分支提交 B1、B2 和事件 E1、E2 在执行时记录真实 ID；文档中的符号不可作为伪造证据。
- 待决动作集合：追加、下一批、修订当前、关联已有、升级前台；候选含明确含义。硬规则预先筛选，不让模型授权越界。
- 时间相关用例使用被测实现公开的超时/新鲜度配置并记录取值；没有定义时先判规格缺口，不能临时猜测。

## 24 个可复现样例

| ID | 初始状态与触发输入 | 明确断言 |
| --- | --- | --- |
| P01 | 在 Xpod Web 依次录入三家测试凭据与 offering；刷新、退出应用再打开；Desktop 重复相同步骤 | 同一账号/Pod 读回自己的配置，其他账号不能读取；三家名称和授权方式正确；界面/日志不出现原始 key；不强求两个独立宿主共用同一内存 Session |
| P02 | 录入有效 OpenRouter 测试 key；请求模型目录，再选已确认 Chat 能力的模型发送“只回答 OK” | 目录和推理各有独立请求证据；响应为有效非空内容且协议解析成功，不强制模型逐字输出 OK；空目录不能当作推理成功 |
| P03 | TypeSafe 使用 state“owner 正在执行兼容任务，追加只增加一条验收”，提问追加/下一批/升级 | 调用实际 System One 入口；choice 属于候选集，记录分数与版本；期望语义为追加。协议成功与语义判断正确分别计分 |
| P04 | OpenCode 分别选择一个已证实协议的普通模型、Jev，再输入缺协议的模型 | 前两者走各自真实协议并校验返回；第三者不能默认为 Chat，UI 与手动 API 路径均给出明确限制；未拿到权威协议证据时该成功分支记 blocked |
| P05 | 本地 Laya state“唯一 owner 忙，新增需求独立且不紧急”；choice 问处置，score 问紧急程度，noul 问是否必须中断当前工作 | choice 期望下一批；score/noul 按部署版本定义校验类型和范围，记录原始量纲，不能自造统一分数；中文语义计分与格式校验分开 |
| P06 | 三个子例：无效 key；不存在的模型 ID；声明 unsupported discovery 的 offering | 认证失败、模型未知、不支持发现分别可辨识；保存 key 不显示已认证；无可调用模型不能绕过选择约束 |
| C01 | 无当前对应任务，用户输入“验收 Xpod 新 provider 的能力声明” | 先记录目标、边界、验收、owner，再派发；唯一任务与执行线；前台只做控制文档和分发，不修改实现文件 |
| C02 | A 正在 rev1，输入兼容变更 rev2；先暂缓 worker ACK，再放行 | 暂缓时 target=rev2、acknowledged=rev1；放行后 ACK 指向 rev2；旧 rev1 Delivery 不能直接满足新增验收 |
| C03 | 唯一可用 owner 正在 reviewing，输入“新增独立的配额显示验收” | 新需求排队，记录容量/就绪原因，原验收不变；owner 释放后重新准入。无关执行线仍运行不能阻止就绪任务启动 |
| C04 | A 正按“全部模型默认 Chat”实施，用户给出 rev3 纠正 | 先记录假设失效与暂停意图；执行端安全点 ACK 后修订并恢复/重启；不得把纠正排到下一批而继续错误实现 |
| C05 | 同一 E1 投递两次，再重放一次超时请求；另发同义用户需求 | E1 不产生重复执行效果；同义需求关联已有任务。传输重试去重与语义重复识别分别留证 |
| C06 | A 最近观察超过新鲜度限制，状态查询失败；用户再请求相同工作 | 显示 unknown 或 observation stale；保留原 owner，先恢复观察，不自行认定闲置或再开一条执行线 |
| C07 | 分别制造低置信、接近的两个候选、返回不存在选项、推理超时；另给一个只有用户能决定的产品取舍 | 前四项进入前台判断；能从现有文档决定的无需问用户，用户所属取舍保持待决并询问用户。每个子例单独报告，不能一例代表全部 |
| C08 | Delivery 的必需测试失败，受控输入给出 accept/0.99 建议 | 接受动作被硬门禁拒绝，任务未关闭；记录建议与最终拒绝。该输入为故障注入，不声称真实模型恰好输出 0.99 |
| C09 | 决策请求绑定 rev1/B0，暂停应用；将记录改为 rev2 或合入 B1，再放行 | 条件应用拒绝旧结果，重新读取并判断；检查与执行间也放入并发变更，不能仅测“读之前已经变了” |
| C10 | 输入标记 local-only，停用本地 Laya，配置的前台为托管模型 | 不向任何外部模型发送该上下文；决策保持 pending 或交已授权本地执行者；网络/调用审计证明没有静默外发 |
| D01 | 一位 owner 提交三方案：通用 adapter 已实测；专用分支仅分析；新增调度器未实现 | 报告逐项标明证据级别、约束、成本、风险、推荐与否决原因；不自动生成三位 worker，不声称三个方案都测过 |
| D02 | worker 退出 0；子例一没有 Delivery，子例二有报告但缺必需测试证据 | 两例均不能 accepted；明确缺什么并要求补交；Run completed 与 Delivery accepted 可独立观察 |
| D03 | owner 发现现有共享类型不能表达 decision，提交证据与 change request | 前台记录差距并选择补契约/调整计划；后台不能改成 Chat 冒充交付，也不能自行删验收 |
| W01 | A 的已接受提交 B1 合入；B 保持未提交修改且仍在 B0 | B 收到目标更新，保护原修改，在安全点更新并跑受影响验收；ACK 前仍标 pending，ACK 后记录真实 B1 和验证证据 |
| W02 | B 更新前先后合入 B1、B2，其中 B2 与 B 本地改动冲突 | 目标最终指向 B2，B1/B2 影响均保留；无未提交内容丢失。Git 冲突与可自动合并但语义失效分别测试 |
| W03 | 当前目标 rev2/B1，B 提交 rev1/B0 Delivery | 不直接接受；生成影响对比，补受影响证据后再决定；保留的无关旧证据必须写理由 |
| R01 | 在 rev2 steer 已发送但未 ACK 时中断控制/执行进程；重启后重放 E1 | 从记录恢复原 owner、pending rev、基线与 Delivery；没有重复任务或双执行，恢复后 ACK 可继续推进 |
| R02 | 加载新 Symphony skill，但执行端缺决策能力或 ACK 功能 | 明确版本和能力缺口，相应用例 blocked；不能显示联合验收完成，也不能隐式切到未声明的实现 |

## 连续故事的执行顺序

成功故事使用同一组 Task/Thread/Run 关联：P01 → P03 或 P05 → C01 → C02 → C03 → D01 → Delivery 证据审查 → W01 → W03 → 当前修订下接受。
失败恢复故事：C07/C10 → 前台处理或用户待决 → 获得所需输入 → R01 → 恢复 → 补交 Delivery。local-only 约束不因用户仅回答业务问题而自动解除。
P02/P04 作为独立接入验收，不与未执行的真实 provider 调用互相顶替。

## 断言与证据归属

- 确定性断言（权限、修订、幂等、ACK、证据缺失、无数据丢失）必须全部成立；任何一次错误接受都失败。
- 语义判断需要冻结标注，含歧义样例的允许结果集合。前台、Laya、Jev 用同一输入做比较；单条正确不能证明模型总体质量。
- 本规格提供功能样例，不冒充统计评测集。完整校准集/保留验收集的数量、标注和质量阈值尚需在真实模型评测前冻结；这是剩余设计项。
- 成功路径使用真实 Xpod、真实测试 Pod 和实际模型；故障注入记录注入点。mock 结果不进入“真实链路通过”一栏。
- 每个 ID 及子例输出 passed / failed / blocked / not-run、预期与实际差异、源修订、版本和证据地址。前台依据证据作验收决定，不由被测模型自行判自己通过。
