# Symphony 决策与分发联合验收计划

状态：2026-09-26，**Xpod case 验收计划，所有运行时用例均待执行**。对应 [升级设计](../symphony-decision-upgrade.md)。
验收对象是 Xpod 的 case，Symphony 负责组织与验收；不测试或发布 LinX 功能。
本轮只审查源码与形成文档。误启动的实现测试已停止，代码已撤回；这些结果不纳入验收。

## 环境与证据契约

- **主验收宿主改为 DSH（DeepSeek Harness）**。Codex 可准备文档、检查结果；实际前台/后台执行链路在 DSH 中验收，不以 Codex 原生任务管理能力替代。
- 本机 `dsh --version` 为 `0.1.5-rc.1`，启动器帮助列出 headless profile；这仅证明入口存在，不证明 Symphony 已加载或任务链路已通。
- 先做 DSH 预检：固定 profile/模型/插件版本，核对 Symphony 实际加载方式，验证任务启动、状态观察、输入/取消/恢复、事件日志与 worktree 工作目录。没有现成能力先记录差距，不悄悄借用 Codex 补齐并算通过。
- 优先使用 headless profile 跑可重复 case；交互升级与用户待决验证使用经预检支持的入口。具体参数在读取本机 profile 帮助后冻结，不猜测配置或安装插件。

- 固定并记录 models、Xpod、执行宿主、Symphony skill、决策 adapter、模型/checkpoint 的版本；实际加载版本必须可观察。
- 使用实际运行的 Xpod Gateway、真实测试账号/Pod，记录实例模式和地址。临时隔离栈和 mock 只能作为补充，不冒充真实实例。
- 找到用户现有 Laya 部署并验证 readiness；云模型使用明确授权的测试凭据。缺凭据则标 blocked/not-run，不能以公开目录访问代替真实调用。
- 准备同一受控测试仓库的目标分支和两个独立 worktree；使用测试账号数据，清理仅限本次产生的资源。
- 准备需求 rev1、兼容追加 rev2、失效纠正 rev3、多方案 Delivery 和刻意陈旧的结果。
- 每条证据记录场景、版本、源修订、输入摘要、实际事件/状态、预期结果、产物链接、结论。报告去除密钥、token、完整私密提示词。
- 模型评测与调度确定性验证分开。受控故障注入可检验门禁，但必须注明，不能算真实模型成功。

## 联合场景矩阵

| ID | 场景 / 操作 | 必须观察到的结果与证据 |
| --- | --- | --- |
| P01 | Xpod Web / Desktop 录入三家 provider，再重启或刷新读取 | 名称和 offering 一致；Pod 中凭据与选择可读回；沿用宿主 Session，不创建平行认证层 |
| P02 | OpenRouter 实际目录发现及一次授权 Chat 请求 | 分别保存目录和有效推理响应证据；空目录不算 Chat 可用 |
| P03 | TypeSafe Jev 实际 typed decision | 实际走已验证 System One 协议，解析结果符合问题类型；不是 chat 假返回 |
| P04 | OpenCode 普通模型和 Jev 模型 | 每模型协议有权威依据并命中对应 adapter；缺协议时显示原因且阻止误调用，含手动选择路径 |
| P05 | 本机 Laya 处理中文 choice / score / noul | 记录实际本地入口、checkpoint、问题与有效输出；输入范围与上下文限制有证据 |
| P06 | key 无效、模型未知、discovery unsupported | 区分已保存、已认证、可发现、可调用；不发布虚假 models/inference 能力 |
| C01 | 用户新需求，前台观察执行线后派发 | 先有文档修订/brief，再有唯一 owner 和 runtime 调度事件；前台不写实现代码 |
| C02 | 运行中追加兼容验收 | 目标 rev 前进，worker ACK 前仍显示旧执行 rev；ACK 后按新增验收执行 |
| C03 | owner 忙或任务临近验收，新增独立需求 | 进入下一批并记录就绪条件；当前验收不变；容量释放后重新判断 |
| C04 | 用户纠正使当前接口失效 | 失效记录、暂停意图、安全点、修订和恢复/重启均可追溯；不延后错误工作 |
| C05 | 重复输入、重复事件、超时后重试 | 同一语义工作不重复派发；事件去重与重试记录可核对 |
| C06 | worker 状态过期或观察失败 | 显示 unknown/pending；不根据沉默推断 idle 或开第二条任务 |
| C07 | 模型低置信、选项接近、无效选项、超时 | 升级前台并记录原因；前台能判断则继续，否则创建用户待决输入；其他线不被全局阻塞 |
| C08 | 模型高置信建议 accept，但必需测试失败 | 硬门禁拒绝接受，记录模型建议与最终判断差异，不关闭任务 |
| C09 | 模型计算中需求修订或目标分支前进 | 旧结果不能应用；刷新快照重判；条件更新与去重防止竞争窗口重复派发 |
| C10 | local-only 文档，本地 Laya 不可用 | 不向云模型或托管前台发送受限上下文；保留 pending 或由已授权本地决策者处理 |
| D01 | 单 owner 评估三方案，仅一方案实现 | 比较报告清楚标明实测/分析/未实现；按实际验收决定能否接受，不伪造三条测试分支 |
| D02 | Run 完成但无完整 Delivery / 缺证据 | 不把退出成功视为接受；要求补交或 change request |
| D03 | 后台遇到无法实现的上游假设 | 提交 change request，前台修订控制文档；后台不自行降低验收 |
| W01 | A 合入，B 在独立 worktree 运行 | 目标 commit 通知 B；B 保护修改、安全更新、重验、ACK；待 ACK 不显示已同步 |
| W02 | 连续两次合入、更新冲突 | 目标可合并到最新 commit，影响集合保留；不 reset 丢工作，语义冲突升级前台 |
| W03 | B 基于旧需求或代码提交 Delivery | 核对差异与受影响证据后重验，不能直接接受旧结果 |
| R01 | 控制面/worker 中断后重启 | 从既有权威记录恢复 owner、修订、pending steer、基线及 Delivery，不靠聊天猜状态 |
| R02 | skill 升级而 Xpod / 执行宿主能力仍旧版 | 明示能力/版本不匹配；不能仅因新文档存在就宣称决策分发可用 |

## 必须跑通的连续故事

具体输入与断言见 [测试样例规格](symphony-decision-cases.md)。24 个场景已有文档样例；自动化脚本、真实凭据与运行证据尚未准备完毕。不得将“样例设计完成”写成“测试通过”。

用一个真实需求走通：录入决策连接 → 前台编写 brief → Laya/Jev 选择 → 单 owner 开始 → 兼容变更追加并 ACK → 独立需求进入下一批 → 多方案报告 → 验收 → 合入 → 第二条执行线更新、重验并 ACK → 陈旧 Delivery 被拦截 → 最终接受。
另走一次失败故事：本地决策不可用 → 前台处理 → 用户待决输入 → 恢复执行。两条故事都要能关联 Task/Thread/Run/Delivery/Evidence；不能拼接互不相关的单测截图。

## 比较评测与发布门禁

新增的提问升级、文件编辑后检查、文档按需补读与 TODO 证据门禁，按 [DSH 实施一致性基准](symphony-dsh-baseline.md) 做 B0–B3 对照与 H01–H16 场景验收；不替代本页 24 项链路场景。

决策质量比较至少覆盖前台直接判断、本地 Laya、选定 Jev 接入。使用同一冻结的中文/多语言场景集，分别记录人工标注、判断正确率、错误接受数、升级率、延迟分布和失败率；有实际计费证据才比较成本。
校准集与验收集分离，样本数与阈值在执行前记录；没有测量不要填写虚构数字。硬约束违规接受必须为零。质量与延迟目标由验收文档明确后才能据此发布，不能看结果后改门槛。

发布门禁：

1. Xpod case 设计、共享契约、skill、Xpod UI 能力声明、实际 adapter 一致。
2. 场景矩阵逐项有结果；blocked/not-run 对应能力不得标已验收。
3. 真实 Pod 读写、Gateway 客户端认证、模型发现、Chat、Decision 分项报告；任一项不能替代其他项。
4. 运行项目要求的构建、类型检查、静态检查与完整集成回归；基线失败与新增失败分开。单元/mock 不能替代这里的真实链路。
5. 最终 Delivery 含多方案比较（适用时）、变更文件、兼容/迁移说明、测试证据、未解决风险、目标版本组合和回退方式。
6. 前台记录 accepted / rework / blocked 及依据；集成和发布状态分别记录。用户授权发布前，不自动发布或部署。
