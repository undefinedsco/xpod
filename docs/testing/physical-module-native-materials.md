# Physical module native materials

`scripts/lib/physical-module-native.ts` is a read-only integrity and relationship validator shared by physical service producers. It does not execute a native member, authenticate a downloaded source, verify signatures, determine license applicability, or approve publication. Its result always leaves `externalAdmission: pending`. Central admission must independently collect and verify actual immutable provenance and acceptance evidence.

The platform supported by a CLI product differs from the format of a native member carried inside its dependencies. Runtime inventory scans actual regular members outside the reserved `source/` and `provenance/` original-material directories, without following symlinks. ELF, thin/fat Mach-O, PE and WASM magic identify carried members; every identified member needs one exact binding, including foreign platform binaries. Native format validation covers Linux ELF 32/64 (ia32, arm, x64, arm64, riscv64), Darwin thin Mach-O and universal containers with non-overlapping valid slices, Windows PE ia32/arm/x64/arm64, and validated version-1 portable WASM. Targets are `linux-<arch>`, `darwin-<arch>`, `darwin-universal`, `win32-<arch>` and `portable-wasm`. This does not add Windows support to ModuleStore or claim a header establishes runtime usability.

## One binding index

`verifyPhysicalNativeMaterials(productRoot, { materialsRoot, indexPath? })` requires two explicit disjoint physical roots. Every ancestor of each root must be a real directory. The runtime retains only a small pre-frozen binding index under `provenance/native/`; the complete original material tree stays outside the runtime. The same index at the same relative path under `materialsRoot` must match the runtime copy by its original bytes, hash and size. Neither root may contain the other.

The index defaults to `provenance/native/index.json`, with `schemaVersion: 1`, `status: native-build-materials`, and `bindings`. Every binding has these exact fields:

- `binary`: an original `SourceFile` reference `{path, sha256, sizeBytes}` relative only to `productRoot`.
- `sourceKit`, `nativeReceipt`, `inputObservation`: the same `SourceFile` shape relative only to `materialsRoot`; no fallback to the product root.
- All local stage receipt/raw references and official API/archive/raw references resolve only under `materialsRoot`.
- `target`: the actual carried format/architecture target.
- `sourceRoot`: a regular directory under `materialsRoot/provenance/`; every ancestor is checked from the materials root. Terms, patches, compiler bindings and kit file inventories resolve relative to this checked source directory.
- `patches`, `terms`, `toolchainInputs`: arrays of the same original `SourceFile` shape relative to `sourceRoot`, drawn exactly from the kit inventory. Terms and toolchain inputs must be present and nonempty; unpatched sources may declare `patches: []`. At least one nonempty source file must remain outside those roles.
- `compilerBindings`: `{field, file}` rows mapping actual native receipt compiler hash fields (for example `cargoSha256`, `rustcSha256`, or `compilerSha256`) to original files in `toolchainInputs`. No package or provider registration is added.
- `observationStage`, `buildStage`, `testStage`: three distinct closed raw records using one of the evidence contracts below.

The source kit retains the existing `schemaVersion`, `status: native-source-materials`, `engine: {repository, commit}`, `toolchain`, and `files` fields used by `packages/xpod-cli/src/native-sources.ts`. All original source files are checked by bytes and inventory membership. The kit's own index may be inside the source directory but is not included in its `files`; no other unlisted regular member or symlink is accepted. Original patches, dependency sources, terms, compiler and sysroot inputs must be collected by the producer into this inventory as applicable. An archive hash alone cannot replace full member inventory/hash verification. Materials may be temporarily expanded into an independently verified task-owned directory for this validator; expanded material and original archives are never recursively copied into the runtime tar. A future strict streaming external source-kit collector can supply that temporary directory after archive readback; it is not implemented by this function.

`nativeReceipt.sourceKitSha256` and `inputObservation.sourceKitSha256` always refer to the original inner source-kit JSON bytes. Reformatting equivalent JSON changes that digest; reserialization and outer archive digests are not substitutes.

The native receipt retains existing `sourceKitSha256`, `helperSha256`, `target`, `engine`, `compiler.toolchain`, compiler hash fields, `buildArguments`, `testsPassed`, `sourceFiles` and `stagedVerifiedFilesOnly` fields. These declarations must match actual original files and a complete source-kit index. `inputObservation` records `schemaVersion: 1`, `target`, `sourceKitSha256`, `helperSha256`, and `filesBefore`/`filesAfter` equal to the exact kit inventory. The independently closed observation raw must parse to the same JSON object. Build/test raw and receipts must also exist and close successfully; a lone `testsPassed: true` cannot substitute for them.

## Evidence adaptation

A local stage is `{kind: local, receipt, raw}`. It directly reuses `scripts/agentfs-native-ci/supervise.py` fields: actual wait, zero exit, no signal/resource stop/supervisor/cleanup errors, owned group absent, timestamp, raw closed before hashing, original raw SHA, and command. No missing PID lifecycle field is fabricated.

An official GitHub stage is `{kind: github, run, job, artifact, archive, raw, sourceCommit}`. Each file is an original hashed `SourceFile` reference relative to `materialsRoot`. The original API bodies must bind a completed successful immutable run and job, exact head SHA, nonexpired artifact from that run/head, and the official artifact SHA-256 to the actual downloaded archive. This branch does not invent local subprocess fields for historical official runs. Fresh API collection, repository/workflow/job identity, strict ZIP/member/log provenance, signatures and admission policy remain the existing central collector's responsibility. Internally consistent stored JSON alone never establishes that it came from GitHub. The caller cannot treat this branch as an authenticated producer attestation.

## Current API status

`bun packages/xpod-api/scripts/pack.ts <product-stage> <fresh-runtime.tgz> <external-materials-root>` is the explicit formal packing interface. The pre-frozen small native index must already exist in both roots. Preview keeps its original two-argument interface and material layout; the new verifier is not used to relabel historic private archives. API formal pack invokes this shared validator after actual source-clean and original-notice checks. Existing Inngest release/source hashes and ACP supplemental terms are incomplete build/toolchain/source evidence and cannot be converted into fictional bindings. A missing or incomplete index therefore blocks release output. A candidate tar, if produced after complete material integrity verification, still carries external acceptance pending; immutable tar bytes are not rewritten to claim later tests passed. Historical private preview bytes and receipts stay separate.

The independent outer module-source-kit artifact is constructed after the runtime tar closes. Its external index and central acceptance receipt bind the actual runtime SHA-256/SRI, exact source build and inner indexes, plus the independent original material archive digests. The inner indexes do not contain the runtime outer tar digest; the runtime does not contain the external source-kit outer archive digest. This order avoids a circular hash or an acceptance-driven rewrite. The existing `xpodModule` product schema and 50,000 runtime member limit remain unchanged. External archive collection, resource budgets, complete source/notices/native proof and actual release acceptance remain pending in the central collector.

Controlled tests use artificial ELF/Mach-O/PE/WASM headers and real short supervised subprocesses. They prove positive and negative validator behavior only. They do not compile a real binary or claim official downloads, compiled dependency closure, or public release clearance.
