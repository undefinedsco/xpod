# Xpod 开发验收与发布流程优化

日期：2026-10-09。范围：登录、Consent、WebID 切换、Local 桌面与 0.4.30 发布。

本轮执行范围与验收标准见 [开发验证与发布效率调整 spec](../superpowers/specs/2026-10-09-development-validation-release-efficiency-design.md)。

这轮耗时来自三方面：缺陷直到安装包或生产环境才暴露，修复与验收脚本修改后不断重启长链路，以及构建、验证、外部等待被排在同一条串行路径上。优化重点是让问题更早、更准确地失败，并让同一冻结输入的证据可核查、可复用。

**单次开发周转应缩短：每次修改只构建受影响的产物、运行能证明修复的测试；完整回归和完整安装验收集中在候选冻结后。** 编译需要保留，但全仓库构建、原生编译、DMG/ZIP 打包不应成为每次修改的默认步骤。同一冻结输入连续执行两轮完整集成也不应作为长期规则。

本文记录复盘事实和后续改造建议，**不修改现行发布门禁**。当前执行规则仍以 [发布流程](../RELEASE.md)、[桌面权限验收](desktop-permission-acceptance.md) 和 AGENTS.md 为准。尤其不能用分支测试代替 exact staging RC，也不能拿 RC 的桌面证据替代不同字节的 stable 安装包。

## 实测时间与主要损失

下表来自 GitHub job 和 step 的时间戳。单个 job 时长不是整条流程的关键路径；并行作业不能相加。重跑列表中会保留先前成功作业，不能把它们算作重复执行。

| 环节 | 本轮实测 | 含义 |
| --- | --- | --- |
| 最终 RC | 42.9 分钟 | 从首个作业启动到 RC 清理结束；不包含此前开发与失败候选 |
| macOS 原生运行时首次建立完整缓存 | job 13.6 分钟，构建步骤 12.6 分钟 | 该轮完整缓存未命中，随后已保存 |
| 同输入原生运行时复用 | 整个 job 18 秒 | C++ 编译与工具链安装跳过，摘要核对和原生 smoke 仍执行 |
| RC 服务镜像构建 | 7.9 分钟 | 与原生构建部分并行 |
| RC 部署与服务验收 | 8.9 分钟 | 包含实际实例认证和业务门禁 |
| RC 桌面作业 | 16.7 分钟 | 包构建约 5.0 分钟，真实权限和操作约 6.0 分钟，另有安装、消费者、自更新等步骤 |
| 正式发布 | 跨三次尝试 108.5 分钟 | 包含外部传播、环境修复和两次重试间隔，不是 108.5 分钟持续编译 |
| npm 发布作业 | 30.6 分钟，其中公网 tarball 等待 25.6 分钟 | 上游传播等待是主要部分，重复 publish 不会解决它 |
| 首次生产部署失败 | 20.7 分钟，其中回滚等待约 10.0 分钟 | 容器尚未启动，旧 Secret 引用阻断新 Pod；回滚镜像也受相同配置影响 |
| 修复环境后的生产部署 | 2.4 分钟 | 同一 accepted digest，未重新构建镜像 |
| stable 桌面作业 | 12.6 分钟 | DMG/ZIP 4.5 分钟，真实权限和操作 6.6 分钟，自更新和组合校验约 0.5 分钟 |
| 冻结源码的一次本地完整集成 | 约 5 分钟 | 最近两轮均为 256 通过、16 跳过；相同输入连跑两次额外增加约一轮成本 |

正式发布作业覆盖北京时间 16:20 至 18:08。这个区间不代表整个开发任务总耗时，也不能推导所有供应商专项用例已经通过。

证据：[最终 RC](https://github.com/undefinedsco/xpod/actions/runs/37899583490)、[原生缓存命中](https://github.com/undefinedsco/xpod/actions/runs/37901388838)、[正式发布及三次尝试](https://github.com/undefinedsco/xpod/actions/runs/37904198548)。

## 为什么测试通过后仍在 RC 失败

测试绿灯只证明其实际覆盖的输入和运行边界。本轮存在产品缺陷、验收驱动缺陷和部署环境缺陷，不能把三者统称为“登录还没修好”。

| 已确认问题 | 之前验证漏掉的边界 | 应前移的验证 |
| --- | --- | --- |
| workflow 的独立 Node 测试还使用旧锁和清理契约 | 当时普通 PR CI 没执行这组测试，直到 RC 才失败 | 已将这组测试纳入普通 PR CI；后续保证新增 runner 的用例也有统一入口 |
| 编译后的 Bun 产物无法加载 SDK 的 bare module | 源码进程能解析工作区依赖，单文件产物不能沿用相同查找路径 | 执行真实 compiled bootstrap 的 SDK lazy loader；验证 staged ESM 文件与依赖闭包 |
| WebID 切换意图在账号预检重新挂载时提前消费 | 普通登录恢复通过，显式切换却复用旧身份 | 切换、重挂载、取消、并发初始化的状态回归；安装包中核对返回的 exact WebID/Pod |
| renderer 用自己的 20 秒预算替换 Task 的 180 秒 signal | 调用层预算正确，跨 renderer 传输后不再正确 | 对真实传输做取消和预算贯穿测试，检查监听器和句柄释放 |
| 验收读取旧 host、用旧 UI 文案定位、错误比较集合键与资源 IRI | 驱动假设与产品/共享模型契约脱节 | 驱动使用共享类型、资源标识和当前 committed host；等待明确 ready，而非固定 sleep |
| Pi 配置未在 A 身份有效时恢复，导致 B 被归属保护拒绝 | 撤销 Key 不等于恢复配置 | 独立验证 A apply/restore、回读完成后切 B；不绕过产品的归属保护 |
| 跨 Pod Run 检查传入空审批体 | 在参数验证层失败，并没有到资源隔离层 | 使用合法请求，断言拒绝发生在 `route_run_read`；仅检查 400/403 不足够 |
| 生产 Deployment 引用不存在的 `connection-url` | 旧 Pod 仍存活，公网健康不能证明新 Pod 可启动 | 发布前核对现有 Deployment 的 Secret/ConfigMap 引用；镜像回滚不能修复坏配置 |
| stable 桌面作业使用 `rc` 环境，但规则只允许 staging | 源码 workflow 测试无法证明 GitHub 服务端策略 | 发布前只读核对目标 ref 的环境许可；所需许可须在启动正式发布前准备好 |

处理失败时必须记录所属类别、最早失败边界、可复现条件和下一步。对未知原因保留“未证明”，不能只根据阶段名称或耗时归因。一次诊断应同时排查同类错误入口，例如凭据类型、资源标识比较、请求预算和等待就绪的约定，避免每修一处才发现下一处同类错误。

## 建议的开发与验收顺序

### 每次修改的最小执行范围

下表是待落地的执行建议，先区分日常修复与候选发布，再调整 AGENTS.md 和 CI 的对应要求。增加测试应针对漏掉的边界，而不是给每个小改动叠加全套验收。

| 改动 | 开发阶段编译 | 开发阶段测试 | 留到候选冻结后 |
| --- | --- | --- | --- |
| 文案、颜色、布局 | UI 开发构建或热更新 | 对应页面与交互检查 | 全量构建、完整集成与完整安装包验收；纯展示修改不单独启动一轮 RC |
| 前端登录或状态逻辑 | 受影响的 UI/共享包及必要依赖 | 状态回归和本次登录、恢复或切换场景 | 全套安装、Task、消费者与发布链路 |
| 后端普通逻辑 | 后端类型检查和相关产物 | 对应单元/集成用例 | 与该改动无关的 UI、原生编译和安装包构建 |
| 存储、权限或跨模块公共契约 | 所有受影响消费者 | 定向回归；影响面广时提前完整集成 | 不因为一次完整集成通过就紧接着再跑相同输入的一轮 |
| SDK 动态加载、Bun 打包或原生边界 | 实际受影响的编译产物 | compiled bootstrap、ABI 或最短实际启动探针 | DMG 制作及与本次故障无关的整段安装验收 |
| 验收脚本或 workflow | 不重建未变的产品产物 | 驱动/Node/workflow 契约；需要时复用已构建包跑对应真实子阶段 | 正式凭证仍须在冻结后的 exact-source 流程生成 |

候选冻结后建议一次集中完成完整回归；提交前核对冻结输入未变，复用这一轮记录。现行两轮要求尚未调整前仍须遵守，不能仅凭本表跳过。正式 staging RC 和 stable 产物验收有独立归属要求，保留其必要检查。

### 快反馈先覆盖最终运行形态

每个修复先用最小回归锁住失败，再运行涉及模块的类型检查和定向测试。涉及打包、动态加载、Electron IPC 或原生 ABI 时，在这个阶段增加真正编译产物的启动探针；源码级 mock 不承担这些证明。

涉及桌面登录、打包或跨进程边界时，定向验证通过后运行该故障对应的最短实际产物探针。例如 SDK 加载只需先执行编译产物的 lazy loader，不需要先制作 DMG，再跑登录、Chat 和 Task 全链路。必须依赖安装形态才能复现的问题才提前制作安装包；其余修改使用开发构建迭代。驱动修改也要有自己的契约测试。诊断可以快速定位问题，但不能输出正式 RC 通过凭证。

这不是取消本地 full 安装验收。完整安装验收仍在冻结源码后执行；早期探针负责减少“跑完大半链路才发现启动或驱动错误”的返工。

### 冻结输入后集中完成门禁

建议固定以下顺序：

1. 完成产品代码、驱动、workflow 和文档修改，审查本轮范围。
2. 核对依赖与补丁状态，记录源码树、lock、工具链、测试命令和夹具版本。
3. 按现行规则完成类型、lint、定向测试和完整集成，记录失败与跳过。
4. 提交本地不可变 SHA，构建 exact-source DMG/ZIP，实际安装并运行完整链路。
5. 通过 PR 普通 merge 进入 staging；对新的 exact staging SHA 运行 RC。
6. RC 全部通过并清理后，核对 accepted tree，通过 squash 同步 main；stable tag 仍指向 accepted staging SHA。
7. 复用 accepted 容器 digest 与原生运行时，验证 stable 包的实际字节、消费者和自更新，再完成正式发布。

若在第 4 步发现缺陷，先回到该缺陷的最小探针，不立即重启完整 RC。修复最终仍要回到冻结门禁；失败记录不覆盖、不追认。

## 哪些验证可以复用

建议新增统一验证回执，包含 source SHA/tree、依赖与补丁摘要、工具链、测试/驱动摘要、环境类别、产物摘要、命令、结果与跳过原因。清理成功、失败阶段和父证据也要独立记录。**是否可复用由输入是否相同决定，不能只看最后修改时间或一句“之前跑过”。**

当前账本把多个阶段快照与最新终态放在一个对象里，发布已完成时仍保留旧的 `pending`、`running` 或 `remaining` 字段。这会让接手者误判状态，重复审计或重跑。建议把不可变事件/历史证据与唯一当前状态分开，当前摘要由事件生成；终态明确关联哪一轮证据，旧失败保持历史状态，不覆盖成通过。每项结果分别标明“未开始、运行中、通过、失败、阻塞、取消”，并指向确切 run/job 或本地回执。

| 变化 | 建议重验范围 | 保留的边界 |
| --- | --- | --- |
| 同一冻结输入，仅准备提交或再次询问进度 | 复核回执和工作树，无需机械重跑同一命令 | 将现行“修复后”和“提交前”两轮要求改成可核查的冻结门禁，需要同步修改 AGENTS.md；修改前继续遵守现行要求 |
| 产品逻辑或共享契约改变 | 定向回归、类型检查、完整集成；按影响运行安装包验收；新 staging RC | 不能把上一 SHA 的整体验收贴到新 SHA |
| 仅验收驱动改变 | 驱动契约测试和该驱动的真实安装链路；正式证据重新生成 | 驱动能把错误写成通过，不能因为“不改产品”就跳过它的真实验收 |
| workflow 改变 | YAML/Action 校验、实际脚本与依赖图契约、secret 边界和失败路径 | 普通产品集成不能证明 GitHub 环境策略；若改变运行产物还需产物验收 |
| 仅文档改变 | 本地链接、事实、格式和规则冲突检查 | 文档不得悄悄放宽门禁；流程契约文档另跑相关契约测试 |
| 仅生产环境引用修复 | 受限补丁校验、配置回读、真实 rollout、新 Pod/digest 与公开门禁 | 不把配置修复写成源码新候选通过；不混入常规镜像提升 |
| 原生输入未变 | 校验并复用完整原生产物，重跑原生 smoke | ABI、工具链、输入或验收脚本改变应失效；整体候选状态不可复用 |
| 外部传播或临时网络故障，输入不变 | 有界重试失败读取或失败 job | 不重复发布相同版本，不重试有副作用的业务写入，不改超时掩盖确定缺陷 |
| stable 版本、签名或包字节改变 | 对最终 ZIP/DMG 重新做权限操作、自更新和消费者验证 | RC ZIP 与 stable ZIP 字节不同，当前两份桌面验收必须保留 |

跨 runner/平台的独立验证不是自动重复。不同 Node/Bun 消费者、Local/Cloud/Standalone、真实 Pod、会话复用与切换均有不同契约。先明确每项证明什么，再通过证据和实测决定是否合并矩阵；不能凭“看起来都在登录”删掉。

## 缩短构建和发布关键路径

### 把环境预检放到发布前

在任何 npm 发布或生产写操作之前，增加只读预检：

- GitHub Environment 对预期 staging/ref/tag 的许可及所需变量/Secret 的存在性。
- 现有 Deployment 的容器、启动参数、Secret/ConfigMap 引用、目标键和非空状态；只输出名称及通过/失败，不输出值。
- 目标数据库、Ingress、存储及资源边界，与本轮 accepted 运行方式一致。
- 更新用旧发行文件和候选原生 artifact 可获取，摘要正确，runner 磁盘有余量。

`CreateContainerConfigError`、缺键、镜像无法拉取等明确不可恢复状态应尽早归因，避免等完整 rollout 超时才发现。但不能仅凭一次 Pending 或短暂初始化就判定失败。回滚后必须单独确认新旧 Pod 的 readiness，不能把“set image 成功”写成“回滚成功”。

stable 桌面和 RC 部署对凭据的需求不同，应评估独立的 stable 桌面验收 Environment，缩小权限面并明确允许 ref。0.4.30 临时收尾只增加了 exact tag 许可，保留 staging 规则；这不应成为每次发布临时改权限的固定流程，也不应靠关闭保护解决。

### 提前构建，等待正确环境后再验收

当前 RC 的桌面 job 依赖服务验收成功，stable 桌面 job 依赖生产部署成功，因而连 DMG/ZIP 构建也在等待后才开始。建议拆成“构建并上传候选包”和“安装并验收候选包”两个 job：

- RC 包构建等待 exact native artifact 和 metadata；服务部署可同时进行。
- stable 包构建在 promotion guard 通过后开始，与 npm 公网传播和生产提升并行；权限操作仍等待正确生产实例。
- 最终上传 Release 等待所有消费者、生产、权限及自更新门禁。
- 两阶段按 SHA、版本和包摘要绑定，验收必须下载原构建 artifact，不在验收 runner 再构建。

本轮 stable 包构建为 4.5 分钟，这部分有机会被外部等待覆盖；具体收益须改造后实测，不能把全部 12.6 分钟桌面验收都算成可消除成本。拆 job 的上传/下载开销也要计入。

### 共享包与原生产物复用按输入管理

完整 QLever runtime 缓存已经奏效，18 秒的命中证据说明不能继续把主要问题归结为“每次重编 QLever”。保留按输入/工具链缓存与新 smoke；冷启动、缓存失效和命中分别统计。

共享包构建在 CI 多个 job、RC prerequisite/验收/finalize 和 stable 构建中重复出现。先统计各包的执行时间与依赖图，再评估一个按源码、lock、构建配置、运行时版本和平台绑定的构建 artifact。下游下载并核对，不共享可被并发写入的 `node_modules` 或可变 dist。仅有上传下载成本高于重建的包，不强行缓存。

`build:packages` 当前串行构建七个工作区包。只有确认依赖关系后才并行独立包，不直接把七个构建全部并发。不同 OS/ABI 产物仍分别构建；已发布共享版本继续按现有 tarball 内容与 provenance 契约复用，不能覆盖同版本。

### 外部等待有界且可续跑

npm 公网传播 25.6 分钟是已观察到的外部等待，不是 TypeScript 构建耗时。继续保留公网 metadata、tarball 下载和 SRI 检查，将已发布版本、integrity 与等待状态持久化；失败后复用已发布字节并只重跑失败下游，禁止盲目重复 publish。

轮询退避可以减少请求和 Agent 唤醒，不能保证上游传播更快。Node/Bun 公网消费者验证仍要保留，不能用 CI 内部下载成功替代公共安装成功。

## 失败诊断与 Agent 协作

失败回执至少给出 stage、substage、固定错误类别、检查项、source/artifact 归属、实际耗时、清理结果和可执行下一步。每个子阶段开始与结束都记录安全进度；原始栈和账号/token/key 只保存在权限受限的诊断位置，不上传公共 artifact。

CI runner 消失时，不能只剩一个 `unclassified`，随后靠重跑完整 RC 补诊断。应保证安全失败摘要在失败分支独立上传；primary 和 cleanup 错误分别保留。等待 ready、资源比较、凭据签发、Task resume 和身份切换使用不同固定子条件。

Lead 的职责是明确范围、审查产物、裁决失败归属和完成最终验收。Worker 独占有边界的文件与任务，开发、自测后在以下节点通知 Lead：形成可审查的文件批次、定向/真实验收结束、确定阻塞或需要扩展范围。无需逐条 shell 指令通知，也不应一直到长流程耗尽才报错。

模型/Worker 切换时交接当前 SHA、改动文件、最后有效证据、失败子条件、自有进程/端口/目录和下一命令；只提供必要上下文。Lead 不与 Worker 重复执行同一检查，不用分钟级读取完整历史维持存在感。等待 CI 时低频查看状态，仅在完成、失败或需要决策时展开日志。WebID 切换清理会话属于产品契约，与 Agent 上下文交接是两件事。

## 实施顺序与验收标准

| 优先级 | 改造任务 | 负责面 | 完成标准 |
| --- | --- | --- | --- |
| P0 | 补齐打包启动、SDK 加载、驱动契约的快反馈入口 | 测试与构建 | 复用已有 compiled loader 与 Node 契约回归；模拟本轮已确认的故障，PR/本地产物探针能先 RED，再在修复后 GREEN；不必占用共享 RC 才定位 |
| P0 | 生产引用与 GitHub 环境/ref 只读预检 | 发布与部署 | 缺 Secret 键或 tag 不被允许时，在发布写操作前给出明确失败；日志无值/凭据 |
| P0 | 统一验证回执和失效规则，调整重复完整回归要求 | 流程与测试 | 同一冻结输入只执行约定门禁；源码、依赖、驱动或环境改变后按规则失效；AGENTS.md 与发布契约同步，不发生隐性放宽 |
| P0 | 区分产品、驱动、环境失败，保留子阶段摘要 | 验收驱动与 CI | 关键链路失败可定位到最早边界；primary/cleanup 分开，公开信息受控 |
| P1 | 拆开桌面包构建与安装验收 job | 发布 workflow | 构建可与环境准备并行；实际验收包摘要一致，最终发布仍等待全部门禁，清理和锁不提前释放 |
| P1 | 统计并复用共享包构建结果 | 工作区构建 | 给出冷/暖对比与下载开销；改输入时失效，跨平台不误用，没有并发污染 |
| P1 | 检查各 CI/RC/job 的相同 SHA 重复任务 | CI 与证据管理 | 按 job id 和输入统计实际执行次数；成功 job 只重试失败下游，不误把历史保留作业算作新执行 |
| P2 | 从长验收中抽取故障专用探针与定期覆盖矩阵 | 产品与测试 | 每个探针有边界与证据；正式安装 full、真实实例和安全隔离门禁不被探针替代 |
| P2 | 规范 Worker 交接与通知频率 | Agent 协作 | 可审查文件、完成/阻塞通知足够；切模型后无需从头重跑，Lead 不重复烧相同检查的成本 |

先实施 P0，再用两到三轮正常发布衡量收益。第一阶段目标是减少返工次数和重复执行，而不是承诺固定分钟数或删掉必要门禁。

每轮记录：冻结到可审查包耗时、PR/RC/正式发布的墙钟与排队时间、job 实际执行次数、失败分类、首次安装验收通过率、原生与共享包缓存命中率、外部等待、清理是否成功。用中位数和较慢轮次比较，冷缓存与暖缓存分开；等待人工授权和供应商故障单列。
