# Xpod 设计自查模板

依据：[DESIGN.md](../DESIGN.md)（产品设计入口）、[产品与体验纲领](product-design-charter.md)与[产品体验实施 spec](superpowers/specs/2026-09-27-xpod-product-experience-spec.md)，版本 2026-09-27 R2。纲领判原则，spec 判具体参数、任务边界和验收；领域权威仍按二者列出的规范执行。

默认只读设计文档；必要时核对前端表达。不要为了填报告启动应用、登录、探查后端、运行完整测试或修改产品。若任务另外授权实施或运行验证，独立记录其范围与结论。

## 一、可以直接派给各路 AI 的提示词

```text
请按 docs/product-design-charter.md，对你负责的 Xpod 模块进行设计自查。

模块：<填写模块 / 用户任务>
文件范围：<填写设计文档；确有必要才补充相关前端范围>
交付位置：<填写报告路径；未指定时用 docs/superpowers/audits/<日期>-<模块>-self-review.md；也可以要求直接回复>
本次授权：只读审查；仅允许写指定报告，不修改产品。

先读纲领、docs/superpowers/specs/2026-09-27-xpod-product-experience-spec.md
及其中与你相关的领域规范，列出适用 D/AC 编号，再检查本模块设计；不要从代码现状
反推设计要求。最多查看前端页面、组件、文案、样式与状态映射，不查服务端
实现，不启动产品或逐个体验功能，不索取账号，不部署、升级或修改配置。

保留Xpod的保存、访问、AI连接及本机管理职责；当前R2组织为概览、存储空间、
AI、服务与访问。内部责任分开不意味着用户必须跨页。你需要举证判断功能和
布局是否成立，不能因为现行文档这么写就全盘接受，也不能擅自放宽安全规则。

按 docs/product-design-self-review-template.md 交付：
1. 说明本模块任务与阅读范围，先交功能取舍、完整决定链、首屏信息预算
   和页型理由；区分用户明确决定与可以重新判断的旧设计。
2. XP-01 至 XP-12 每项给出符合 / 偏离 / 缺证据 / 待裁决 / 不适用，
   标注是文档层还是前端层的判断，并附实际阅读材料的位置。
3. 对问题说明违反的规则、相反证据、用户影响、最小修正方向、责任模块
   和可检查的完成条件。没有证据时不要写成实现缺陷。
4. 单列跨模块冲突。先辨别对象和范围，再应用领域规范的覆盖关系；
   已有明确决定的直接引用，仍缺决定的给出选项与影响。
5. 区分本模块修正、公共设计系统修正、需要统一决定的事项。
6. 保留值得保留的设计，明确未覆盖范围。

你不是独自在工作区，不覆盖他人的修改，不派生新的共享规范或主题。
审查通过不等于功能已实现或运行已验证；缺少运行证据不是本次设计审查
的通用阻塞条件。不要用截图数量、测试数量或总分代替设计判断。
```

## 二、报告模板

以下为报告结构。删除未使用的说明文字；没有问题时也需要提供逐项判断的依据，不必为凑数制造问题。

### 范围与职责

- 模块 / 负责人：
- 审查日期 / 纲领与实施 spec 版本：
- 适用设计决定 D 编号 / 实施验收 AC 编号（本轮不冒充已做运行验收）：
- 用户任务（一句话）：
- 场景（桌面 / Web / 云端 / 本机 / 自托管，只列适用项）：
- 本模块负责 / 不负责：
- 前置模块 / 完成后去向：
- 审查层次：文档；或文档 + 前端表达。
- 已阅读的文件、章节或行号：
- 未覆盖范围：

### 适用依据

| 依据 ID | 文件与位置 | 适用对象 / 规则摘要 | 性质 |
|---|---|---|---|
| E-01 | `<实际路径#章节或行号>` | `<规则>` | 用户决定 / 领域规范 / 历史材料 / 前端表达 |

源文件中的“已实现”是该文件的声明；若未阅读对应前端或运行证据，不扩大为本次验证结论。前端组件的存在只能支持对应表达，不证明请求成功、持久化正确或权限安全。

### 功能与操作是否成立（先于规则合规）

| 功能 / 入口 | 用户要作的决定 | 没有它哪条任务受损 | 保留 / 合并 / 降级 / 条件显示 / 删除入口 / 待证实 | 理由和受影响能力 |
|---|---|---|---|---|
| | | | | |

为1–3条主要任务列出：意图 → 用户必须决定的点 → 系统自行读取/校验的阶段 → 明确副作用 → 完成/部分失败恢复。区分文档推导与实测，不编造点击次数或使用频率。质疑既有规则时给出处、替代方案和权衡。

| 场景 | 首屏结论与关键事实 | 强调动作（允许没有） | 专业详情如何可达 | 当前页型及密度理由 |
|---|---|---|---|---|
| 正常 / 首次 / 停止 / 未知 / 异常（列适用项） | | | | |

气质验收必须指向行为与信息结构：正常是否安静、失败是否清楚、决定是否可预测；不能只用颜色或“高级/克制”作证。

| XP-05 用户控制与改变后果 | 待填写 | 文档 / 前端 | |
| XP-06 失败与恢复 | 待填写 | 文档 / 前端 | |

| XP-10 品牌与操作气质 | 待填写 | 文档 / 前端 | |
| XP-11 公共设计系统与归属 | 待填写 | 文档 / 前端 | |
| XP-12 可访问性与异常状态 | 待填写 | 文档 / 前端 | |

判定含义：

- **符合**：本次审查层次所需的明确规则与材料一致；注明证据，不能据此声称功能已跑通。
- **偏离**：有明确适用规则，且阅读材料中有相反表达；列出两者。
- **缺证据**：本次层次缺少必要说明、状态设计或前端材料；写出缺什么，不假定结果。
- **待裁决**：适用规范仍冲突，或涉及尚未决定的共同规则；不是“实现麻烦”的替代说法。
- **不适用**：对象、宿主或职责不适用并说明理由；不能用来隐藏未设计的必要状态。

### 关键任务契约

选本模块最重要的 1–3 条任务填写；简单模块可只填一条。不要求为每个按钮重复一张表，也不要求运行产品。

| 项目 | 设计说明 / 前端表达位置 |
|---|---|
| 用户要完成什么，作用于哪个对象 | |
| 前置条件，由哪个模块负责 | |
| 主动作与改变范围 | |
| 提交、进行中、完成各说明什么 | |
| 等待、失败、部分完成时如何恢复 | |
| 取消、返回或离开会发生什么 | |
| 完成后去哪里，保留哪些上下文 | |

这些是体验检查维度，不是要求各模块新增一套相同的运行状态枚举。未涉及的状态标不适用；依赖现有 canonical 的直接引用。

### 问题记录

每个独立问题一条，共同根因只维护一条记录。

```text
问题 ID：<模块>-DESIGN-01
标题：<具体偏离及其用户影响>
判定：偏离 / 缺证据 / 待裁决
优先级：P1 / P2 / P3
关联原则：XP-xx
审查层次：文档 / 前端
适用规则：<依据 ID + 原文要点>
实际材料：<相反表达，或明确缺少的内容 + 文件位置>
用户影响：<影响谁完成什么，不猜测未验证的后端结果>
最小修正方向：<先修职责、文案、状态或归属，避免默认重构>
主责模块 / 关联模块：
完成条件：<可以重新检查的文档或前端表达结果>
未验证边界：
```

优先级服务于设计排期：P1 为核心职责、身份/授权/数据操作契约、任务闭环或错误承诺；P2 为影响理解、操作和公共一致性的局部问题；P3 为不改变主要任务的细节完善。按用户影响判断，可访问性问题也可能是 P1。不要将设计风险直接升级为已发生的安全漏洞或数据损失。

### 跨模块事项与交接

| 问题 ID | 主责 / 消费模块 | 可直接引用的决定，或待决定的问题 | 各模块需同步什么 | 完成条件 |
|---|---|---|---|---|

需要新决定时，写出相互冲突的依据、选项及用户影响。已有领域规范可以裁决的，直接列决定来源，不重复向用户确认。依赖未定事项的部分挂起，其余独立检查继续。

自查不自动授权修正。若另有实施授权：本模块可在分配范围内对齐已确定的规则；公共主题、组件和术语由共同责任方统一修正；一级导航、产品职责、身份与权限、自动化和数据操作语义不能由局部实现顺手更改。

### 结论

- 最重要的设计结论（不超过三项）：
- 值得保留的设计：
- 本模块可修正事项 / 公共层事项 / 待决定事项：
- 本次仍缺少的设计或前端材料：
- 本轮结论范围：仅设计审查；或设计与前端表达审查。

不得以“全部通过”省略范围。也不要因为没有启动产品，就把已经完成的文档审查写成无法开展。
