# Matrix Pod 存储可移植性：存储决定与实现契约

更新：2026-09-26。

状态：**存储归属已确定：消息、同步日志、去重记录及必要执行凭证全部持久化到 Pod。SQL journal 是待移除的旧实现。**
待定项仅是 Pod 内协议的具体实现与迁移验收，不再讨论是否长期保留 SQL journal。
单文档条件写测试不能替代完整协议验收；实现缺口需要在 Pod 方案内解决。

分布式目标与协议职责以 [协作设计](matrix-collaboration-design.md) 和
[决策登记册](matrix-collaboration-decisions.md) 为准：参与者数据落各自 Pod，跨 Pod 分发
已在目标范围；原单共享 Pod adapter 只代表当前实现。

## 已确定的边界

Matrix 的会话数据（Chat/Thread/Message/Delivery/Run/RunStep）与成员、Agent 授权状态，
必须以参与者 Pod 内的持久资源为权威存储，结构化事实采用 RDF；完整协议事件的验证材料
必须无损保存，不能只保留消息展示投影。共享 schema、关系与资源布局归
`@undefineds.co/models`；Xpod 实现协议 adapter，不复制共享模型。

业务语义不得依赖 SQLite 扩展列、QLever 私有查询或只能在某个部署运行的会话数据库。
同步 journal 负责事件引用、已发布位置与增量读取；去重记录负责请求重放；执行凭证负责来源
与内容核验。三者职责分开，必要持久状态都在 Pod，不能靠本地同步索引是否存在决定执行资格。

本地加速索引、队列和缓存只承载派生或临时状态，必须能从 Pod 完整重建。丢失本地状态不得
破坏消息去重、同步完整性、执行授权、尝试预算或终态；在途租约丢失按既定恢复协议处理。
重建位置空间时使用显式 epoch 和客户端重同步，不得静默跳过事件。仅迁移正文不足以实现
这一目标，事务映射、发布记录及凭证也必须落入 Pod。

### 区分两类可移植性

1. **Xpod 支持的存储后端**：同一 Xpod API、授权与存储接口下，切换 SQLite、PostgreSQL、
   QLever 等后端组合，Matrix 的可观察行为应一致。身份 SQL 数据库与 Pod RDF 后端是不同
   能力轴，不能混称为一个 provider。身份库的存在不赋予 Matrix 在其中持久化上述状态的例外。
2. **第三方 Solid/CSS 部署**：不得假设拥有 Xpod 的 `/-/sparql`、相同 PATCH 媒体类型或
   可用于 CAS 的强 ETag。接入前必须验证所需能力，不支持时明确拒绝相关能力或采用已经
   验证具有相同语义的通用实现，不能静默退化为不安全写入。

当前 Message/Thread 声明 `/.data/-/sparql`，Chat 声明 `/.data/chat/-/sparql`。
ORM 根据已声明 endpoint 选择 SPARQL 策略；没有声明时可走 LDP。**这不表示已声明但不可用
的 endpoint 会自动安全回退，也不表示任意第三方 Pod 都提供这些路径。**

[Solid Protocol](https://solidproject.org/TR/protocol#writing-resources) 要求支持 N3 Patch，
但 RDF 表示的强 ETag 是 MAY；不能从符合 Solid 协议推导出所评估的条件写协议需要的全部 CAS 能力。
读取与条件写应通过同一能力接口适配，禁止在 Matrix 业务逻辑散落后端身份分支。

## 三层同步的状态都落 Pod

一个逻辑房间可跨部署与参与者 Pod。同一 homeserver 可服务多个用户，不假设一个用户或
Pod 必须对应一个独立 homeserver。协议服务身份与 Pod 访问能力的对应关系需要落实，
这不重新打开跨 Pod 分发的范围决定。

| 层次 | 必须持久化的内容 | 不可混用 |
| --- | --- | --- |
| homeserver 之间 | 交易/事件接收、验证、缺失依赖与补发进度 | 不等于客户端 since 或目的 Pod 已全部写入 |
| 本部署到参与者 Pod | 接收资格、每个目的 Pod 的事件投递及部分失败进度 | 一份副本成功不代表全体成功 |
| Pod 到客户端 | 本 Pod 的发布引用、授权可见状态与增量读取位置 | 不是全房间全局顺序或服务器交易确认 |

各项记录需明确其承载 Pod 与访问主体。未能写入最终目的 Pod 的接收数据，若需要先持久
确认，必须在 Pod 内有可恢复的接收记录；不能让本地 SQL 或内存成为唯一恢复依据。

客户端事务去重、服务器交易去重、事件副本去重与 Agent 执行去重各有作用域。同步 journal
只承担其中的发布/读取职责，不兼任所有可信证明和执行状态。

判据是：更换部署、清空本地派生状态后，能从相应 Pod 恢复投递、同步、重放及执行事实。
不是每个参与者 Pod 必须存所有人的密钥或控制记录，而是每份必要事实都有明确、可访问的
Pod 归属。浏览器只需持有客户端状态，不要求浏览器缓存或复制全部历史。

## Pod 同步日志必须保持的不变量

高水位必须满足：读者推进到 N 后，不会再出现需要以 ≤ N 的位置交付、此前尚不可见的事件。
这里要求的是已发布事件前缀，不要求所有整数都必须对应事件。

裸序号分配会出现 A 拿到 7 尚未提交、B 拿到 8 先提交，读者越过 7 的问题。Pod 内协议必须
将事件发布与可见位置关联；CAS 一个计数器不等于提交整个事件。协调可限定在 Pod 内，
但热点 Pod 的争用仍需验收，不能直接宣称瓶颈消失。

## Pod 实现必须满足的协议要求

[Matrix 事务规范](https://spec.matrix.org/v1.18/client-server-api/#transaction-identifiers)
要求按设备和端点识别重放，并考虑请求路径；已识别重放应返回原响应状态与内容。
`/sync` token 是不透明位置，不要求全局 SQL 序号。

规范不指定存储方式；本项目已决定用 Pod 实现去重、稳定重放与不漏增量。可信执行触发、
内容冲突检查及崩溃恢复所需的持久状态同样进入 Pod，并保留各自独立的职责。

## 实现契约：Pod 内事务记录与事件发布

以下约束用于落实已确定的 Pod 存储决定。条件写、资源布局、分段和证明机制仍需细化及
验证；这些实现选择尚未定案，不表示存储归属待定，也不表示已经实现或验收通过。

### 1. 事务记录与文档级条件创建

- 事务键包含 Pod scope、认证身份/设备及完整端点作用域；当前发送接口至少包含 roomId、
  eventType、txnId。使用稳定的结构化编码和版本域，不能只 hash(scope, device, txnId)。
- 确定性键用于定位事务记录，不自动决定所有历史 eventId。记录须保存首次 eventId、
  创建时间、规范化内容指纹、目标消息引用与提交阶段；保留旧事件 ID。
- `If-None-Match: *` 只保护整个 HTTP 文档。当前 models 把同日消息存为
  `messages.ttl#a`、`messages.ttl#b`，不能用这个条件头保证单条 Message 首次插入。
  实现需为事务记录定义可独立条件创建的资源，或另行设计并验证文档内条件更新。
  不得未经 models 设计就改变 Message 日期分桶布局。
- 底层收到 412 后，读取原事务记录，核验请求并恢复原响应；412 不直接作为正常 Matrix
  重放响应。不同内容按明确的冲突契约处理，不能覆盖首次接受的请求。
- 若事务记录先创建、Message 后写入，记录必须含可恢复载荷或指向已持久化载荷的引用。
  只有 hash 无法恢复正文，也不能解决上一轮发现的“结果预留后、正文写入前崩溃”。

新共享控制资源、状态字段和布局必须先在 models 定义，持久 RDF 读写优先使用 drizzle-solid。

### 2. 已发布位置必须绑定事件引用

**不能把“CAS 分配下一个数字”当作“发布一个事件”。**

一个可评估的发布顺序是：

1. 持久化可恢复的事务意图和正文，确认目标事件可精确读取且内容符合回执。
2. 用一次条件写，在同一发布资源内同时增加 `sequence → event reference` 和已发布高水位。
   这一成功写入是事件进入同步位置空间的线性化点。
3. 后续补齐事务完成标记、Delivery 与调度状态；重复恢复识别已发布事件，不重复分配位置。

这种方案仍需定义并验证：同一事件的发布去重、发布失败后的恢复、并发冲突重算、原生 Pod
消息发现，以及正文与索引查询之间的可见性。读者必须从发布记录定位事件；若 SPARQL 索引
尚未可见或目标暂不可读，不能静默略过并推进游标。

单个发布文档不能无限增长。分段、归档、段间链接和高水位更新涉及多个资源，其切换协议
必须单独定义并接受同样的崩溃验证。另一种候选是 pending/committed 状态与连续发布前缀，
但必须明确未完成位置如何恢复或终结。具体资源形态和分段方案目前未定。

| 中断点 | 必须保证的恢复行为 |
| --- | --- |
| 事务意图创建后、正文前 | 从持久载荷继续写；不能只剩 hash 且阻止所有后续执行 |
| 正文已写、事件未发布 | 补发布一次；不能形成永久孤儿或重复事件 |
| 发布成功、响应丢失 | 读取原发布记录，返回原 eventId/位置，不再追加 |
| 发布成功、Delivery/Run/队列确认前 | 从提交记录补齐状态，已完成结果不重新执行 |
| 位置资源缺失、损坏或恢复旧备份 | 检测并停止推进；按显式恢复流程更换 epoch，不静默从 0 开始 |

claim 到 Run 持久化之间的尝试次数丢失也需独立解决；替换游标和事务表并不会自动修复队列终态。

### 3. 保留执行来源的信任边界

执行来源证明持久化在 Pod，独立于用于同步的 journal。API 接受的用户触发和助手结果
必须能够核验，不能将任意直接 Pod 写入当作已授权执行来源。

具体证明机制需选择并验证，例如仅受信服务可写的证明资源，或可验证的签名记录。
两者均需明确签发主体、可修改范围、验证者信任来源和跨部署迁移方式；签名方案另需密钥
轮换、撤销和历史证明验证。普通消息作者可写的 metadata、确定性 ID 或资源存在性不能充当证明。

证明应绑定身份、作用域、事务/事件标识、内容及执行关联，防止跨房间、跨角色重用。
提供 executor 消息写权限不等于应提供证明或高水位的任意写权限。服务代写也必须先验证
调用者当前 Pod、成员和 Agent 授权，不能借服务权限扩大调用者的访问面。

Pod 执行凭证投入使用前必须完成独立 executor 身份的实际 ACL 验收，并决定 Pod owner 直接修改数据
后哪些事实仍可展示、哪些不得继续触发执行。

### 4. 条件写能力与 ORM 约束

优先在 drizzle-solid 补齐显式条件写/冲突返回能力。安装版的部分 412 重试路径会刷新 ETag
再重发旧 PATCH；这不等于重新读取状态并重算业务决定，不能用于该 CAS 协议。

若上游能力缺失阻塞实现，先维护 [原子性问题记录](issues/drizzle-solid-matrix-atomicity.md)，
再将临时 HTTP adapter 限定在条件写原语；不得手工复制业务 RDF 模型或默认豁免全部 ORM 读写。
冲突必须返回决策层重算，不能无条件重放旧决定。

ETag 必须与据此计算新状态的表示来自同一版本。写入响应无 ETag 时，下一轮可重新 GET
取得状态及对应 ETag；**不能把后续 HEAD 得到的较新 ETag 配给旧状态继续写**，因为中间可能
已有其他写者。超时或响应丢失属于结果未知，需按操作标识核验，不能当作写入失败直接再分配。

接入能力门禁至少验证：所用 PATCH 媒体类型、条件创建、强验证器、并发旧版本拒绝、
不同表示的验证器语义、重启后的版本行为，以及授权查询/写入的能力范围。能力不足时明确拒绝
启用该条件写实现；不得回退到盲写或恢复 SQL 权威存储。

## 资源形态提案（待定案，不表示已实现）

以下按前述提交契约给出候选形态，用于收敛讨论；**尚未定案、尚未实现**。

### 前提一：消息形状是 Solid Chat 的，且与 app、协议无关

`Message` 的谓词来自 Solid Chat 词表，**没有协议或会话类型分支**：

| 字段 | 谓词 |
| --- | --- |
| chat ← message（反向） | `wf:message` |
| thread ← message（反向） | `sioc:has_member` |
| 父容器 | `sioc:has_parent` |
| 作者 | `foaf:maker` |
| 正文 / 富文本 | `sioc:content` / `sioc:richContent` |

群聊与私聊、Matrix 与其它 app 的差别只落在**取值**：`foaf:maker` 是 WebID、agent URI 还是
contact URI，以及 `metadata` 里放什么。消息文档仍是
`/.data/{parent.dir}/{yyyy}/{MM}/{dd}/messages.ttl#{id}`。

**因此不得为 Matrix 的某个机制去改消息布局、日期分桶或加协议分支。** 首次创建、去重或会话类型相关的行为应由相应协议层处理，不得借此引入
另一套 Message 布局。

### 固定载荷重放与协议事件身份

RDF 集合语义只保证同一组固定三元组重复插入不增加同样的 triple；含新 blank node、不同
正文或重新生成时间的写入不满足这一前提。事务记录必须先固定首次标识与载荷，并检查
内容冲突和提交阶段；不能据此省略整个消息提交协议。

Matrix event_id 依所选 room version 生成/验证，跨副本保持一致。当前讨论的
[room version 11](https://spec.matrix.org/v1.18/rooms/v11/#event-ids) 使用事件 reference hash，
不能采用 `$ + hash(Pod URI)` 替代。事件图、签名和授权链中的引用在复制时不改写。

**Pod 中的 Message URI 是持久存储地址，不是浏览器缓存。** 两个参与者的 Pod 可各有一份
对应资源，地址不同但协议 event_id 相同。需要可按 event_id 定位事件，但不强制增加独立
映射表或镜像库；可由共享 schema 中的协议标识、资源寻址及可重建索引实现。

消息资源地址由 models 的布局规则构造，协议事件身份独立于目的 Pod 的地址。不再采用
`messageUri ← hash(eventId)` 与 `eventId ← hash(messageUri)` 的循环公式，也不认为正文
变化会自动产生另一个合法事件资源。客户端同事务不同内容应由首次事务记录判为冲突。

旧随机 ID 不直接重算成新协议 ID。它们缺少的签名/事件图材料不能补造；旧房间兼容或
导入新房间的迁移规则需单列，并保留原引用可追溯性。

### 候选一：事务记录独立资源（承载去重及可恢复提交）

- 路径按事务键的结构化编码确定性派生，覆盖 Pod scope、认证身份/设备、完整端点作用域
  （roomId、eventType、txnId）与版本域。
- 记录内容：首次 eventId、createdAt、规范化内容指纹、目标消息引用、提交阶段，以及
  **可恢复载荷或指向已持久化载荷的引用**（只有 hash 无法恢复正文，也不能解决结果预留后、
  正文写入前崩溃）。
- 创建用 `If-None-Match: *`：首次 201；重放 412 → 读回记录、核验请求、返回**原响应**；
  412 不作为正常 Matrix 重放响应返回客户端。内容不同按冲突契约处理，不覆盖首次接受。
- 正文仍按前提一写进 models 的 Message 文档；本资源只是它的回执载体，不复制消息语义。

### 候选二：发布日志（分段 + 开页 CAS）

- 发布点必须**在一次条件写内同时完成**"分配位置"和"写入事件引用"，所以发布单元是
  **一个文档**，不是计数器资源——计数器只能表达"下一个数字"，不能表达"某数字对应哪个事件、
  且该事件已可见"。
- 文档增长用分段：段内自包含 `sequence → event reference` 与段内高水位；段满封闭，
  只对**开页**做 CAS 追加；读者按段链推进。
- 读者从发布记录定位事件；若 SPARQL 索引尚未可见或目标暂不可读，**不得静默略过并推进游标**。
- 原生 Pod 消息的发现有界化：晚到消息必须仍被发现，发现扫描只能在有界窗口内进行，
  不能按 createdAt 截断。
- 位置资源缺失、损坏或恢复旧备份时，检测并停止推进，走显式恢复流程更换 epoch，不静默从 0 开始。
- 不要求跨 Pod 全局单调序号。若采用其他客户端增量机制，仍需证明晚到事件发现、
  分页稳定、token 与查询量有界、状态变化可见及清空派生状态后的恢复。已见事件集合本身
  不提供变更发现，不能仅因不需要全局序号就删去发布机制。

### 尚未验证

- 同一文档上的并发 CAS 追加重试语义（本仓库实测只覆盖顺序请求：201/412/205）；
- "段满封闭"是否需要条件写，以及封闭与追加的原子性；
- 事务记录的可恢复载荷保留多久、何时可回收；
- 分段大小与读者回溯窗口取值；
- 共享持久 schema 归 models 已定；待细化的是复用现有资源还是新增定义、具体字段和布局。

## 旧 SQL journal 的迁移与移除

以下仅记录旧实现依赖和退出步骤，不构成目标架构中的 SQL 存储选项。

| 旧记录 | 必须迁入 Pod 的状态 |
| --- | --- |
| `xpod_matrix_transactions` | 原事务键、首次 eventId/createdAt/contentHash、资源引用，以及当前用于触发和交接核验的回执 |
| `xpod_matrix_events` | 事件引用、发布关系及可验证的迁移位置；新位置空间通过版本/epoch 与旧游标区分 |

旧实现的 PostgreSQL BIGSERIAL、事件表锁、建表 advisory lock 及 SQLite AUTOINCREMENT
随 SQL journal 一并退出；不将其改造为长期权威存储。旧表只在有界迁移/回滚阶段保留，
期间与 Pod 配套备份。目标是运行时不再依赖这两张表。

迁移不是简单删表后让客户端重新同步：

1. 采用停写切换或可证明的单写者切换协议，停止旧写者和消费者；先保留一致性备份。
2. 将原事务键到原 eventId、createdAt、contentHash、资源引用的映射迁入 Pod，迁移仍需使用的可信
   触发/结果回执与未完成任务。跨日定位仍使用首次时间，不用迁移时间生成新 ID。
3. 新位置空间使用可区分的版本和恢复 epoch，并绑定 scope；格式由实现定案，不能继续用
   无法辨别来源的 `v2_<seq>`。切换后旧 token 明确返回 `M_UNKNOWN_POS`，再做全量同步。
4. 验证旧 txn 重试仍返回原 eventId、不重复消息；授权、pending 任务、尝试预算和已完成
   结果仍有一致解释。明确历史回执的保留范围，不能静默丢弃旧幂等承诺。
5. 校验导入数量、映射和内容绑定后才能切换。新系统开始接受写入后，不得直接切回旧 SQL；
   需先停止写入并回迁增量，或明确回滚窗口已关闭。
6. 完成切换与恢复验收、关闭回滚窗口后，删除旧表/索引、建表逻辑和运行时依赖。旧备份按
   约定期限退出，不保留永久双写或长期 SQL 回退路径。

## 性能目标与可移植性同时验收

批量查回执、批量登记以及请求内授权复用可以减少调用，但不是消除全历史扫描的证明。
同步分页应按发布位置读取有界事件集；正常 claim 与历史恢复分离；续租不得依赖整个 timeline。
原生 Pod 消息需有可靠增量发现或有界对账，不能以创建时间过滤丢弃晚到消息。

Pod CAS 会增加网络往返，同 Pod 争用、发布文档增长与分段成本必须测量。接口后端适配可以
不同，但 Matrix 行为与验收契约保持一致；不能以可移植为由接受无界扫描。

## 授权读取缓存：现状及限制

当前工作树的 `SubgraphSparqlHttpHandler` 实现了跨请求的判定缓存：键包含目标、主体、
client 与模式；本 handler 成功写入递增所推导 Pod 范围的世代号；允许和拒绝均缓存，TTL 为 5 秒。

**这是授权新鲜度的改变，不是无条件等价优化。** 未命中重新判定不代表旧 allow 命中时仍然
满足最新权限。普通资源写入或另一实例撤权后，旧允许记录仍可能在过期前命中；拒绝缓存也会
延迟新授权生效。TTL 是缓存项寿命，不是已经验证的端到端最大撤权窗口，在途判定和请求仍需考虑。

生产门禁必须明确可接受的撤权语义，验证真实 Pod 根范围、祖先 ACR、普通 ACL/ACR 写入、
跨实例及在途请求。当前进程内 epoch 不能宣称已提供跨实例失效。

**当前实现仅局部绕过缓存，修复目标是停用跨请求 allow/deny 缓存。**
现有 `x-xpod-authorization-fresh` 标记由 agent-wakes 上下文传至 Pod fetch，再由 SPARQL
处理器跳过跨请求缓存，覆盖 claim/renew/complete/fail；普通 Matrix 路径仍使用缓存。
这不等于全局授权修复已完成。当前修复阶段只保留请求内复用，恢复跨请求缓存须先有明确
新鲜度契约和可靠失效验收；不能把未决撤权语义当作继续保留旧 allow 的理由。

本地新鲜判定不意味着已知尚未送达的远端房间撤权。协议事件授权与 Agent 执行的当前授权
分别处理；在途请求、网络分区和执行归属方不可达时的行为需明确，不承诺全网瞬时一致。

`ObservableResourceStore` 目前仅 cloud 挂载，local 未挂载，不能把它作为已经覆盖全部模式
的失效来源。没有可靠失效支撑时采用请求内复用；跨请求缓存不得作为已接受的优化保留。缓存性能通过不能替代权限正确性验收。
