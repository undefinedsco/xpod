版本：2026-09-28 R6 文档校正；保留 R2 本机控制面参数。用途：统一各模块的设计判断，供设计、前端及负责不同模块的 AI 自查。

**R5 目标依据**：[个人 AI 产品故事](../../homepage/docs/specs/personal-ai-product-story-r5.md)将“训练你的 AI，让它学会你的判断”确立为主叙事，补充知识、任务与模型训练目标。R2 的本机布局、认证和运行管理继续有效，但不再代表完整产品价值，也不能据此宣称新增个人 AI 流程已经全量覆盖。目标画面见[R5 画板](../../homepage/docs/reference/personal-ai-r5/index.html)，新增审查 PA01–PA07 按该 spec §7 执行。

## 一、先对齐我们在做什么

### 1. 长期方向决定产品取舍，眼前价值决定使用入口

产品源头是 Coco，AI 提供了从日常工作留下记录的现实入口。北极星是：**个人日志合并在一起，就是整个文明的历史。**

这意味着记录本身值得保存，不因某个模型、应用或公司更替而失去价值；记录应容纳个人的立场、偏见与改变。它不要求用户先认同“延续自己”的宏大需求，也不意味着默认公开、归集全部资料、用于训练或自动替用户决策。

用户先把今天的事做好，再决定愿意留下什么。保存、删除、访问和分享由本人掌握。Our Vision 负责讲远处；操作界面负责让当下的事情清楚、可控。

### 2. 产品分工

| 层面 | 主要职责 | 设计判断 |
|---|---|---|
| LinX | 以工作、知识、我的 AI 组织日常协作、编辑和反馈，由用户定义方法并从取舍中成长 | 协作中的示范、纠正、来源与个人模型使用可检查；普通成果保存是支持流程 |
| Xpod | 承载资料、个人知识、任务及个人模型资产 | 数据主权、本体、索引/Wiki与任务分别有操作依据；不能缩减为存储控制台 |
| Xpod 桌面 | 管理资产所在空间、授权、索引覆盖、AI 接入和服务 | 四入口只限定本机控制器；用资源定位连接 LinX/Foundry，不复制聊天、知识编辑或训练表单 |
| AI / 个人模型 POM | 通用能力与经授权训练、评估的个人模型共同参与工作 | 个人模型是明确产品目标，训练就近标规划状态；知识检索不等于模型已训练 |

“Xpod 是纸”是解释保存关系的隐喻，不要求把产品做成纸张装饰或文件办公应用。强调数据归属也不自动推出网盘首页。R2以概览、存储空间、AI、服务与访问组织本机控制面任务；旧五工作区不是不可审查的用户决定。页面需要什么布局，取决于用户在做什么，而不是后台分了几个模块。

日常用户、自部署用户和开发者应看到同一套事实；通过摘要、详情和专业入口适配信息深度，而不是各自维护一套产品真相。

裁决规则：

1. 用户最新明确决定优先；同一问题已有领域 canonical 明确覆盖旧规则，直接按其裁决并注明来源。
2. 品牌、产品交互和安全权威各管其范围。更亲近的文案不能改变身份判定，更温暖的配色不能取消状态语义。
3. 对象不同的规则先分开：运行配置密钥、提供方凭据和 Xpod 客户端密钥不是同一对象。
4. 计划、路线图、历史审查和旧版截图是背景或证据，不自动成为新规范。
5. 规范之间仍有实质冲突时，登记双方、作用范围与待决定事项；不得选择最方便实现的一份，也不得各模块发明临时规则。
6. 规范与前端不一致时分别记录“目标要求”和“前端表达”。不改规范迁就现状，也不凭规范宣布实现完成。

## 三、十二条跨模块设计原则

### XP-01 · 用用户要完成的事解释产品

页面首先帮助用户作判断或完成动作：现在能否使用、资料或服务位于哪里、什么需要处理、下一步去哪里。准确的技术名称保留在需要它的任务中，避免让用户先学习内部架构才知道该点哪个按钮。

**自查**：逐项功能写出谁需要作什么决定；删除该入口会损害哪条任务？判定保留、合并、降级、条件显示或删除入口，并保留底层能力边界。只有内部名词没有用户决定，不能证明它应常驻。是否越界复制LinX，或把本机管理能力藏得无法使用？

### XP-02 · 愿景、设计目标和交付事实分别表达

“规划如此”“前端有入口”“已发布”“当前环境已验证”是不同事实。文案、示意图、状态标签和帮助页采用一致的能力边界。用户拥有资料，不等于默认本地推理、永不外发、全天在线、无限保存或任意应用完整互通。

**自查**：每个能力承诺写明适用场景与依据；无法支持的承诺收窄或列为待核实。设计审查通过不等于运行验证通过，缺少运行证据也不自动使一份设计不合格。

### XP-03 · 对象明确，事实有来源

Account、WebID、Pod、宿主机、Xpod 服务、模型商连接、Xpod API Key、模型发布版本及 Run 分别有职责和权威来源。界面可以简化解释，不能合并事实。切换对象、授权、导出、迁移和删除时，用户应能辨认动作的目标与范围。

产品级切号遵守 9/19 X-1，先隔离并清理旧 WebID/Pod；“退出管理账号”“断开 WebID 会话”是另行明确命名的单层动作，不能把其隔离规则套给产品切号。训练用途授权不由资料读取权推导，撤回授权也不代表已训练权重自动遗忘。

**自查**：“已登录”“已连接”“可用”具体指什么？有没有用账号成功推导 Pod 权限、用进程存在推导服务健康、用一种凭据代替另一种？不得为自查再造会话或状态机。

### XP-04 · 意图、执行和观察结果分开

保存配置、提交操作、正在执行、需要重启或重建、检查通过、任务可用分别表达。未知、未配置、空数据、无权限和读取失败不能相互替代；会过期的观察结果说明检查范围与时间。

Foundry 发布目标、runtime 实际可服务版本、客户端已选版本和 Run 实际使用版本分别举证；候选、发布、启用和实际使用不能以一个“就绪”覆盖。服务健康、任务依赖、知识积累、运行时适应和模型训练也分别表达。

**自查**：每个成功提示到底证明了哪一步？是否把目标配置直接显示成运行事实？刷新失败是否把旧值当作实时状态，或把取不到的数据显示为零？

### XP-05 · 用户能理解改变，也能改变主意

创建空间、扩大访问、改变保存位置、重建索引及删除等动作遵守领域规范中的明确选择要求。已有自动化应有清楚的作用范围、触发条件和可用的停止或调整路径；打开页面本身不代表新的授权。

保存位置、外部 AI 请求去向、访问权限和训练用途分别说明。权限撤销不能被描述为能够收回对方已取得的副本。普通可逆操作不因此统一增加确认弹窗；确认强度与实际后果相称。

**自查**：用户在改变发生前能否理解对象、范围与后果？是否把产品愿景当成默认收集、分享或训练的授权？

### XP-06 · 失败可理解，恢复回到原任务

错误表达“哪里失败、影响什么、现在能做什么”。局部失败保持局部影响，不能把资源读取错误表达为账号退出。恢复保留安全范围内的输入、已完成步骤与任务上下文，遵守原有身份和权限校验。

从 LinX 知识、模型版本或 Run 发起的修复保留原对象、合法版本、用途及返回位置，修复后重新校验权限、材料范围和成本；不自动提交训练、不换模型或重建 Key。继续原 Run、修复依赖和重新发起训练分别受其 owner 控制；结果未知先查询原操作，取消请求不冒充执行已停止。

**自查**：设计是否覆盖适用的等待、失败、重试、取消和部分完成？持续等待有没有反馈与出口？取消等待与撤销操作是否混淆？不能只设计成功截图。

### XP-07 · 模块分工明确，用户任务连续

AI接入负责提供方、模型可用事实、Xpod Key与客户端接入；AI配置负责用途选择，两者在R2共享AI入口。内部边界必须保持，但不因此强迫用户跨一级导航。围绕完整任务组合已有视图：用户只为目标、授权、保存位置、覆盖、成本等有意义的决定行动，系统负责读取与校验；确需跳转时保留原任务。

**自查**：是否有重复的凭据管理、状态解释或设置入口？失败能否回到正确模块修正？任务不断点，不等于把所有模块合成一页。

### XP-08 · 生命周期与数据操作采用准确动词

关窗、退出界面、退出账号、停止服务、禁用连接、撤权、删除分别说明影响。导出说明能拿到什么，备份说明能恢复什么，迁移说明源与目标及连接影响。原始资料、可重建索引及持久模型产物必须区分；已发布 adapter/checkpoint 不因属于派生产物就成为可删缓存。导出/备份范围涵盖清单、来源、版本和实际字节，外部 artifact store 单列；只有指针不算完整可恢复。停止、升级和退出按实际依赖说明本机 Run、远端训练与未来调度的不同影响，未知影响如实说明，不隐含暂停、撤权或取消。

**自查**：按钮、确认和完成反馈是否描述同一个动作？失败或取消后哪些部分已改变、哪些仍保留？未交付的后台代理、迁移或恢复能力不得写成现成出口。

### XP-09 · 信息架构由任务证明，密度按页型分配

导航保持可预测，物理列数不必相同。概览、对象集合、配置、诊断分别采用合适页型：真正集合才有对象列，固定章节不强塞中栏；读写事实分区，不必分成两个工作区。专业详情有稳定入口，低频不等于删除，也不必常驻。四入口只限定本机控制器，资产与运行详情通过原对象到达；知识精读、评估对照复用公共视觉而不硬塞诊断行或认证小窗。

**自查**：按正常/首次/停止/未知/异常写首屏信息与主动作；算实际视口下可见的条目/选择，指出滚动是否用于当前任务。每行字段与动作是否同等重要？用户是否必须理解内部分类才能完成任务？不能把“符合旧导航”作为布局已成立的证据。

### XP-10 · 温暖、现代、日常、能干，服务于清楚操作

纸色和墨紫建立亲近感，清晰的层次、状态与动作建立工具感。功能界面主要使用无衬线；版本、地址和诊断值可用等宽。大留白、书信排版与宏大叙事留在合适的阅读场景，不进入每个操作页面。

**自查**：除色板外，正常时是否安静、故障时是否清楚、行动时是否能预测结果？可选能力未配置是否被做成长期告警，界面是否让用户照看内部进程？给出具体信息顺序、动作和反馈证据，不能只写“温暖/高级”。同时检查选定Logo和主题，不将官网Hero字号/大间距套入桌面。

### XP-11 · 共用一套设计系统，业务由模块表达

语义 token、基础控件、焦点和公共认证展示由 shared-ui 承担；布局及宿主能力适配由 extension-sdk 承担；业务数据、路由、产品文案和页面组合由应用承担。模块复用同类交互，不复制公共控件，也不在共享层烘焙单页业务。

**自查**：这次差异需要新的业务组合，还是复制了一套按钮、弹层、主题或状态含义？共享问题交给公共层责任方；各模块不得分别修出不同版本。

### XP-12 · 可访问性与异常状态是基本设计内容

选中、禁用、错误和运行状态有文字、图标或形状依据；颜色只是辅助。标签持续可理解，图标操作有名称；键盘路径、焦点进入与返回、窄窗导航、长文案和内容滚动在设计中有交代。

**自查**：不靠鼠标、仅看文字状态、遇到长错误提示或窗口变窄时，用户还能理解并完成任务吗？只存在默认态设计或只有正常页面 CSS，不能覆盖这些结论。

## 四、品牌映射的共同基线

以下是 2026-09-26 已选定方向的摘要，用于审查；不是另建一套页面私有 token。

| 角色 | 基线 | 产品使用约束 |
|---|---|---|
| 画布 / 下沉层 / 浮起层 | `#F7F4ED` / `#F2EDE2` / `#FBFAF7` | 按内容层级使用，不机械交替铺底 |
| 正文 / 次要文字 | `#2B2621` / `#655D53` | 功能标题与正文以可读性为先 |
| 主操作 / hover / pressed | `#563E84` / `#4B3672` / `#402E61` | 紫色用于操作和标记，不给普通标题全部着色 |
| 装饰线 / 控件边界 | `#DFDBD5` / `#87837D` | 装饰线不能独自承担控件识别；tint 上强边界用 `#655D53` |
| 选中与焦点 | 明确标记；焦点 2px 墨紫轮廓与 3px 间隔 | 保持公共控件的一套实现，避免重复焦点框 |
| 状态 | 文字和图标先成立 | success / warning / destructive 的语义保留；颜色映射由公共主题统一，不各页自配 |
| Xpod Logo | 留缝折角；应用墨紫底，站内与 LinX 配对用纸底 | 使用选定资源和专用小尺寸版本，不自己重画；旧资产保留 |
| 字体与密度 | 功能界面无衬线，桌面信息密度，适量留白 | 不引入外部字体依赖，不套营销页大字号、大间距 |

正文小字对比度目标 ≥ 4.5:1，必要控件边界与图形 ≥ 3:1；需按实际前景 / 背景组合检查。仅看到 token 名不能证明对比度合格。

现行产品有跟随系统主题的要求。新主站未覆盖的桌面深色、语义状态、菜单栏状态映射与平台资产输入，已由[9/27 产品体验 spec §8–§9](superpowers/specs/2026-09-27-xpod-product-experience-spec.md)作为**本次设计补全**统一规定；不代表系统图标已打包或各平台已验证。各路 AI 不私配主题，正常、等待、空态、错误、禁用、焦点和选中均消费同一映射。

## 五、每个模块应守住的职责

| 模块 | 核心自查问题 | 需要协调的事实 |
|---|---|---|
| 桌面 Shell / 托盘 | 启动、关窗、退出、后台运行各自表达是否清楚；导航、主题、焦点是否稳定 | 服务生命周期、登录与退出结果 |
| 概览 / Status领域 | 当前实例、可用范围、原任务依赖与下一步是否优先；可选未训练是否保持中性 | 宿主在线、服务健康、网络可达、Pod访问、知识覆盖、训练及Run结果分别表达 |
| 服务与访问 / Network领域 | 一次连接任务能否完成，推荐地址、范围、配置与实测是否清楚 | 规范地址、Status 观察结果；不自行改变身份标识 |
| AI 接入 | 连接、模型、客户端配置及修复返回原任务是否连续 | 发布目标、实际服务版本、客户端选择与Run使用记录分开；凭据不混用 |
| AI 配置 | 用途、模型选择、保存、生效和索引重建是否区分 | 复用 AI 接入和索引事实，不复制凭据管理 |
| 账号 / WebID / Pod | 当前对象与关系是否清楚；无 Pod、多 Pod、冲突和恢复的设计是否完整 | 使用各自权威；创建空间是明确动作 |
| 授权 / 访问 | 哪个应用取得什么权限、作用于哪个目标、撤销影响什么 | 上游凭据、Pod 授权、Xpod 客户端密钥分别管理 |
| 存储 / 用量 / 迁移 | 保存/执行/产物位置、原始/索引/持久模型、外部字节和恢复范围是否明确 | 身份、地址、授权、任务及连接变化；费用/配额/容量有各自范围与时间 |
| 公共设计系统 | 同语义的控件、布局、文案注入和状态映射是否共用 | 不拥有业务事实；统一处理影响多个模块的问题 |

这些是审查责任域，不要求新增同名页面，也不构成强制新增功能清单。实际能力不支持时，应准确呈现支持范围；不能为了填满表格制造假入口。

## 七、各路 AI 如何自查与交付

默认采用**文档审查**；确有必要时补**前端表达核对**。不以完成自查为由启动应用、登录账号、遍历功能、调用模型、部署或升级。服务端、数据库和协议实现不在本轮自查范围。若另有明确实现或运行验证任务，按该任务单独开展，结论另列。

每个模块只交一份自查记录，复用[统一模板](product-design-self-review-template.md)：

- 先写职责、场景、文件范围与适用规范，避免审错对象；区分用户明确决定、继承设计、本轮建议，允许举证质疑现行设计。
- 在逐项合规前，先交功能取舍表、1–3条完整操作链、各状态的信息预算与布局理由；不能直接将所有现有功能/页面判定为必需。
- 对 XP-01 至 XP-12 逐项给出结论：**符合 / 偏离 / 缺证据 / 待裁决 / 不适用**，并指向本次实际阅读的章节或前端位置。
- 结论必须标注审查层次。“设计符合”和“前端已表达”不等于运行已验证；设计层没有要求运行证据的项目，不因未运行而一律判“缺证据”。
- “偏离”同时列规则与反证；“缺证据”具体说明缺少哪个设计或前端材料；“不适用”说明原因；不要输出没有依据的全勾选或综合分数。
- 每项问题说明用户影响、最小修正方向、责任模块与可检查的完成条件；共同根因使用一个问题记录，其他模块引用它。
- 自查本身不授权修改。若另有实施授权，只在分配范围内修正已明确的问题；共享主题、一级导航、状态含义、权限和跨模块契约由相应责任方统一处理。
- 冲突有现成规范可裁定时直接记录结论；仍缺决定时给出选项与影响。只挂起依赖该决定的工作，继续其他独立检查。

一轮自查完成的标准是：**适用原则有判断，判断有对应层次的依据，缺口有明确归属，未定事项没有被伪装成决定。** 它不要求凭空实现缺失能力，也不以逐个体验全部产品功能作为前置条件。
