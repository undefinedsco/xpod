# Matrix 协议服务身份与 Pod 归属：契约草案

日期：2026-09-26。状态：**草案，未定案、未实现**。用于收敛决策登记册里"协议服务身份与
Pod 归属"这一项；不表示任何能力已存在或已验收。

依据：[决策登记册](matrix-collaboration-decisions.md)、[协作设计](matrix-collaboration-design.md)、
[Pod 存储契约](matrix-pod-storage-portability.md)。历史实现范围见设计文档"迁移与当前实现现状"。

## 1. 要解决的问题

Matrix 的复制单位是**参与房间的 homeserver**：homeserver 有域名、有签名密钥、签发事件、
参与状态解析。而 Xpod 的 Pod 是**存储空间**，不是协议实体——它没有域名、没有签名密钥、
也不天然代表某个用户。

于是必须先把下面这条线画清楚，否则"房间跨 Pod"会退化成"多条互不相认的副本"：

| 概念 | 归属 | 不是 |
| --- | --- | --- |
| 协议服务身份（server name + 签名密钥） | 部署 | 不是 Pod，也不是 WebID |
| 用户身份 | WebID ↔ MXID 映射 | 不是 Pod |
| 房间身份 | 逻辑房间（稳定 room_id） | 不是某个 Pod 里的资源路径 |
| 事件身份 | event_id，按 room version 规则生成 | 不是 Pod URI 的 hash |
| 存储位置 | 参与者自己的 Pod | 不参与协议身份 |

## 2. 身份与映射

| # | 身份 | 形态 | 现状 |
| --- | --- | --- | --- |
| I1 | 协议服务 | server name（如 `xpod.example`）+ Ed25519 签名密钥对 | 仅有部署级 32 字节根密钥基建（`src/security/secret-cell/`），**无 Ed25519、无 signing key、无 key 发布端点** |
| I2 | 用户 | MXID `@<localpart>:<server name>`，localpart 由完整 WebID 派生 | 已有：`@u_<sha256(webId)>:<serverName>` |
| I3 | 设备 | device_id 由 WebID + 认证 clientId 派生 | 已有（无 clientId 时回退 gatewayKeyId） |
| I4 | 房间 | 稳定 `room_id`，随房间存续不变 | 已有随机 room_id；不含跨部署语义 |
| I5 | 事件 | event_id 按 room version 规则生成 | 消息为随机 `$...`；结果事件为 hash（内部用途）。**均非协议合法事件 ID** |
| I6 | 执行身份 | Agent / executor（WebID） | 已有，见第 6 节 |

关键约束：

- **一个部署可以承载多个用户与多个 Pod**，因此不能把"Pod"当作"homeserver"，
  也不能把 WebID 域名当作 server name。
- **Pod 迁移不改变用户与房间的协议身份**；变化的只是副本的存储地址。
- I1 的 server name 一经参与房间即不可随意更改（它会进入 MXID 与事件签名）。

## 3. 事件身份与签名

### 3.1 event_id

按所选 room version 的规则生成并校验；**不得**用 Pod 资源 URI（或其 hash）代替。

room v11 使用事件 **reference hash**，形如 `$<unpadded-url-safe-base64>`，由事件按该版本的
**redaction 算法**规整后做规范 JSON 编码再 sha256 得到。

> **实现前必须按规范核对的两个细节**（本草案不复制规范正文）：
> 参与 hash 的字段集合，以及规范 JSON（键序、Unicode、数字）的具体规则。
> 核实来源：Matrix Spec 的 room version 11 章节与 event hashes 说明；本机无法访问
> spec.matrix.org，需在实现阶段以仓库内可复现的方式（如对照 synapse/complement 测试向量）
> 固定下来。

### 3.2 签名

- 每个参与房间的部署用自己的 Ed25519 密钥对事件签名；
- 签名对象是事件的规范 JSON；验证方按事件声明的 origin 取该部署的公钥；
- 公钥发布端点：`/_matrix/key/v2/server`（Matrix 服务器密钥发布约定）。

**现状缺口**：仓库无 Ed25519 实现、无签名密钥、无 key 发布端点，也没有事件验证代码。
这一层是分布式能力的硬前提，不能靠现有 `MatrixHandler` 的“事件形状”补齐。

### 3.3 验证材料必须无损保存

Solid Chat 表示是**共享消息表达**，不是完整可验证事件：当前 `Message` 投影会丢掉原始
事件 JSON、签名与状态解析所需字段。

因此持久层需要同时保存：

1. **Solid Chat 表示**（供人读与跨 app 互通，遵守既有形状与日期分桶）；
2. **原始事件与签名**（供协议验证、历史回填与状态解析）。

两者的资源布局、字段与索引**必须先在 `@undefineds.co/models` 定义**，Xpod 只做 adapter。
不得只存展示正文而丢掉协议事实。

## 4. 房间的 Pod 归属与投递

### 4.1 副本与身份

- 一个逻辑房间有**一个稳定 room_id**；每个有资格的参与者可以在**自己的 Pod** 里持有副本。
- 副本之间的存储 URI 可以不同；**副本地址不产生新的协议事件身份**，也不授权改写已签名
  事件内部引用的 URI。

### 4.2 谁写谁

- **用户写自己的 Pod**：用调用者自身权限（caller-owned），不借用他人存量密钥。
- **接收服务写目的 Pod**：使用**明确获授的部署能力**，并校验目的参与者的事件接收资格；
  不扩大到调用者访问面之外。
- 远端事件的 `sender` **不是**可以被重放的 Solid 凭据。

### 4.3 资格判定

投递前必须能回答"这个 Pod 的拥有者在**该事件的历史可见性**范围内吗"。这要求：

- 房间成员与状态解析结果可按事件位置求值（状态解析本身也依赖第 3.3 节的验证材料）；
- 成员加入前的事件不可见、邀请不等于获得对方 Pod 写权；
- 历史可见性的判定规则需要在实现契约中写成可执行断言，而不是口头约定。

### 4.4 投递进度是每个目的 Pod 的持久事实

- "服务返回成功"不等于"对方 Pod 已持久化"；每个目的 Pod 的投递进度单独持久化；
- 部分成功必须可恢复：投递记录在源侧或目的侧择一并写进契约，不能只存在于一次响应里；
- 客户端同步是从**自己的 Pod** 提供增量，与跨部署投递进度是两件事，不得混用同一游标。

## 5. 三种同步的边界

| 层 | 职责 | 不可混淆的状态 |
| --- | --- | --- |
| 部署间同步 | 传输与验证事件、缺失事件获取、历史回填、状态解析 | 服务器交易/接收状态，不是客户端 since |
| 部署 → 参与者 Pod | 按资格与可见性持久化已接受事件，恢复部分成功投递 | 每个目的 Pod 的投递进度 |
| 客户端同步 | 从自己的 Pod 提供授权范围内增量与分页 | 客户端 token / 本地发布位置 |

## 6. 执行归属

- 消息复制与执行调度是**不同操作**；逻辑触发关联稳定的 `room_id` + 触发 `event_id` +
  目标 Agent + 用途，**不得**按各副本的 message URI 生成彼此独立的任务身份。
- 必须指定执行**归属方**与承载控制事实的 Pod；其他 Pod 复制执行事件**不获得执行权**。
- 多实例接替必须服从同一控制事实，不能靠互不共享的 Redis 租约或"各自看到 pending"抢占。
- Delivery/Run/RunStep 继续使用共享模型，并由 schema 明确区分"向某 Pod 投递消息"与
  "向 Agent 交付工作"；模型与 attempt 语义先在 models 定义。
- 执行仍至少一次；工具以稳定逻辑操作 ID 幂等。

## 7. 待定决策

| # | 决策 | 选项 | 影响 |
| --- | --- | --- | --- |
| D1 | server name 粒度 | 甲：部署级单一 server name；乙：每个 Pod/租户一个 server name | 决定密钥数量与 `/_matrix/key/v2/server` 的解析方式；乙更接近"每 Pod 一个 homeserver"但要求每个 Pod 有可解析域名与密钥 |
| D2 | 签名密钥的生命周期 | 生成/存储/轮换/历史事件验证 | 轮换后旧事件必须仍可验证；密钥不得与用户凭据混用 |
| D3 | 原始事件与签名的资源形态 | 独立资源 / 图内节点 / 其它 | 必须先入 models；与消息投递如何在一次写入内保持一致 |
| D4 | 跨部署传输协议 | 复用 Matrix Federation API 子集 / 自定义 | 决定兼容面与验收方式 |
| D5 | 旧数据迁移 | 旧随机 event_id 的房间与消息 | 不能通过开关变成合法 room v11 历史；只能保留历史兼容面或导入新房间 |
| D6 | 执行归属方的选择规则 | 房间创建者 / 首见事件方 / 显式声明 | 决定 claim 与接替的控制事实落在哪个 Pod |

## 8. 验收草案（对齐设计文档门禁）

| 门禁 | 必须证明 |
| --- | --- |
| 身份映射 | MXID/设备稳定；Pod 迁移不改变用户与房间身份；server name 变更需显式迁移 |
| 事件身份 | 同一事件在两个部署/两个 Pod 副本中得到同一 event_id；篡改任一字段后验证失败 |
| 签名与验证 | 公钥发布可解析；伪造 origin、错误签名、缺字段的事件被拒绝（fail closed） |
| 投递 | 部分投递失败可恢复；重复投递不产生第二个事件身份；投递进度持久且可重建 |
| 资格 | 加入前事件不可见；邀请不授予写权；撤权后新同步不再包含未授权副本 |
| 执行归属 | 副本不产生独立执行；接替服从同一控制事实；无有效接替授权时不得抢占 |
| 恢复 | 清空本地派生状态后，仅凭 Pod 可重建同步、投递与执行记录，且不复活已终态任务 |

## 9. 本草案不覆盖

- 具体 room version 的完整事件授权规则（power levels、`m.room.create` 约束等）——
  属"事件验证"实现契约；
- 客户端 API 的扩展（滑动同步等）；
- E2EE、跨部署媒体、账号迁移；
- 性能与容量结论（见存储契约的性能门禁）。
