# Matrix 协议服务身份与 Pod 归属：契约草案

日期：2026-09-26。状态：**修订后的目标契约，未实现、未验收**。承接已定的 Matrix 分布式与 Pod
持久化目标；第 7 节仅列实现待办，不重新打开产品范围。

依据：[决策登记册](matrix-collaboration-decisions.md)、[协作设计](matrix-collaboration-design.md)、
[Pod 存储契约](matrix-pod-storage-portability.md)。历史实现范围见设计文档"迁移与当前实现现状"。

## 1. 要解决的问题

Matrix 的复制单位是**参与房间的 homeserver**：homeserver 有域名、有签名密钥、签发事件、
参与状态解析。而 Xpod 的 Pod 是**存储空间**：Pod URL 可以有自己的域名，
但这不自动赋予它 Matrix server name、事件签名身份或用户身份。

于是必须先把下面这条线画清楚，否则"房间跨 Pod"会退化成"多条互不相认的副本"：

| 概念 | 归属 | 不是 |
| --- | --- | --- |
| 协议服务身份（server name + 签名密钥） | 逻辑 homeserver，可由多个服务实例承载 | 不是 Pod，也不是 WebID |
| 用户身份 | WebID ↔ MXID 映射 | 不是 Pod |
| 房间身份 | 逻辑房间（稳定 room_id） | 不是某个 Pod 里的资源路径 |
| 事件身份 | event_id，按 room version 规则生成 | 不是 Pod URI 的 hash |
| 存储位置 | 参与者自己的 Pod | 不参与协议身份 |

## 2. 身份与映射

| # | 身份 | 形态 | 现状 |
| --- | --- | --- | --- |
| I1 | 协议服务 | server name（如 `xpod.example`）+ Ed25519 签名密钥对 | 仅有部署级 32 字节根密钥基建（`src/security/secret-cell/`），**无 Ed25519、无 signing key、无 key 发布端点** |
| I2 | 用户 | MXID `@<localpart>:<server name>`，localpart 由完整 WebID 派生 | 已有：`@u_<sha256(webId)>:<serverName>` |
| I3 | 设备 | device_id 由 WebID + 认证 clientId 派生 | 已有（无 clientId 时回退 gatewayKeyId） |
| I4 | 房间 | 稳定 `room_id`，随房间存续不变 | 已有随机 room_id；不含跨部署语义 |
| I5 | 事件 | event_id 按 room version 规则生成 | 消息为随机 `$...`；结果事件为 hash（内部用途）。**不能作为合法 room v11 历史的依据** |
| I6 | 执行身份 | Agent / executor（WebID） | 已有，见第 6 节 |

关键约束：

- **一个部署可以承载多个用户与多个 Pod**，因此不能把"Pod"当作"homeserver"，
  也不能把 WebID 域名当作 server name。
- **Pod 迁移不改变用户与房间的协议身份**；变化的只是副本的存储地址。
- I1 的 server name 一经参与房间即不可随意更改（它会进入 MXID 与事件签名）。

### 2.1 逻辑服务与部署

一个逻辑 homeserver 使用稳定 server name、签名身份及一致的持久处理状态，可以由多个
实例共同承载。扩缩容、地址迁移和服务发现委派不产生新的协议身份。一个部署承载多个
server name 时必须隔离各自的密钥与路由；不要求每个 Pod 单独成为 homeserver。
服务发现遵循 [Matrix server discovery](https://spec.matrix.org/v1.18/server-server-api/#server-discovery)，
连接目标地址不能替代原始 server name 成为验签身份。

### 2.2 WebID、MXID 与目的 Pod 的绑定流程

1. 从已验证的登录上下文取得 WebID，不接受请求正文声称的 WebID 作为身份证明。
2. 在本逻辑 homeserver 下创建或恢复唯一的本地 MXID 绑定。现有 WebID 哈希仅是命名方式，
   不是账户控制权证明；不得据此冒领远端 MXID。
3. 用户明确选定承载 Matrix 数据的 Pod，并用自身权限证明对目标资源范围的控制权。
   WebID 所在域、登录服务地址、Pod 地址可以不同；拥有多个 Pod 时不得任意选择第一个。
4. 将绑定及其版本、目的存储范围、服务授权引用持久化到用户选定的 Pod；本地索引可重建。
   schema 由 models 定义。服务重新挂载时从经认证的用户提供/确认的 Pod 入口恢复绑定，
   不依赖不可恢复的 SQL 映射。
5. Pod 迁移时，先复制必要事实并验证新地址授权，再切换绑定版本；并发投递必须核对版本，
   对切换窗口内旧地址上的写入完成补迁后才退役旧绑定。失败时保留可恢复的迁移状态。
   MXID、room_id 和 event_id 不变；更换 homeserver 不是单纯的 Pod 地址迁移。

设备生命周期另行建模；当前 WebID + clientId 的派生实现不证明不同浏览器/设备可独立撤销。
设备验收必须覆盖独立登录、凭据轮换与撤销，不能只检查派生字符串稳定。

## 3. 事件身份与签名

### 3.1 event_id

按所选 room version 的规则生成并校验；**不得**用 Pod 资源 URI（或其 hash）代替。

[room v11](https://spec.matrix.org/v1.18/rooms/v11/#event-ids) 使用事件 **reference hash**，
形如 `$<unpadded-url-safe-base64>`。按版本的 redaction 算法规整，移除 `signatures` 和
`unsigned`，再按 Canonical JSON 编码并计算 SHA-256；字段处理必须遵守该版本的 PDU 规则。
内容 hash、reference hash 和签名承担不同职责，不得混用。

实现须固定规范版本及可复现测试向量，覆盖字段排除、键序、Unicode、数字限制和 redaction；
不能把本地序列化器的普通 JSON 输出视为规范编码。

### 3.2 签名与验证

- 签发事件时先计算内容 hash，再对按 room version redaction 后的事件执行规范的 JSON
  签名过程（排除 `unsigned`、`signatures`），将签名附回事件。
- v11 按 `sender` 所属服务器验证必需签名，并执行适用的额外签名要求，例如 restricted
  join 的授权服务器签名。不得由事件自行声明的 `origin` 决定可信发送者。
- 事件可以由第三方服务器转发。Federation 请求认证用于确认本次传输方，事件签名用于
  验证事件签发身份，两者分别校验；不能要求每个接收副本的服务重新签发事件。
- 通过 server name 和 key ID 获取及校验服务器密钥；公钥发布使用 `/_matrix/key/v2/server`。
  密钥响应签名、有效期、旧验证密钥与事件时间的检查遵循所选版本的规范，不能只取裸公钥。
- 签名失败、结构不合法及事件授权失败按协议处理。签名有效但内容 hash 不匹配时，使用
  协议规定的 redacted 副本继续处理，不能发布未验证正文，也不能一律当作签名失败。
  `unsigned` 变化和合法 redaction 不应被错误拒绝。

依据：[Signing Events](https://spec.matrix.org/v1.18/server-server-api/#signing-events)、
[v11 授权规则](https://spec.matrix.org/v1.18/rooms/v11/#authorization-rules)。
事件 ID 一致或签名有效都不能替代事件授权、依赖获取与状态解析。

**现状缺口**：尚无完整 Matrix 签名密钥管理、key 发布端点和事件验证链。
这一层是分布式能力的硬前提，不能靠现有 `MatrixHandler` 的“事件形状”补齐。

### 3.3 验证材料必须无损保存

Solid Chat 表示是**共享消息表达**，不是完整可验证事件：当前 `Message` 投影会丢掉原始
事件 JSON、签名与状态解析所需字段。

因此持久层需要同时保存：

1. **Solid Chat 表示**（供人读与跨 app 互通，遵守既有形状与日期分桶）；
2. **原始事件与签名**（供协议验证、历史回填与状态解析）。

两者的资源布局、字段与索引**必须先在 `@undefineds.co/models` 定义**，Xpod 只做 adapter。
不得只存展示正文而丢掉协议事实。

## 4. 房间的 Pod 归属与投递

### 4.1 副本与身份

- 一个逻辑房间有**一个稳定 room_id**；每个有资格的参与者可以在**自己的 Pod** 里持有副本。
- 副本之间的存储 URI 可以不同；**副本地址不产生新的协议事件身份**，也不授权改写已签名
  事件内部引用的 URI。

### 4.2 谁写谁

用户交互请求使用调用者自身权限。异步接收则使用目的 Pod 控制者明确授予服务主体的能力，
两者具有各自的授权上下文；不要求远端消息发送者具有目的 Pod 写权。

服务授权必须限定主体、目的资源范围和允许操作，并有明确的撤销入口。入房邀请既不创建
Solid 写授权，也不授予工具执行权。服务不能借用其他用户存量 owner 密钥；远端事件的
`sender` 不是可重放的 Solid 凭据。授权引用不等于授权本身，写入前须作新鲜判定。

目的 Pod 撤销服务写权后停止写入，保留受控的待处理状态并告知本地用户需要恢复授权；
不得借其他凭据绕过。当前修复阶段停用跨请求 allow/deny 缓存，只保留请求内复用。
本地重新鉴权不代表已经收到远端成员撤权；远端状态仍按协议传播和解析。

### 4.3 资格判定

按事件位置的房间状态和已知成员历史判断目的参与者资格，不能只看当前是否在房间。
依据 [历史可见性规则](https://spec.matrix.org/v1.18/client-server-api/#room-history-visibility)：

| 事件位置的条件 | 判定 |
| --- | --- |
| `world_readable` | 允许读取历史；不因此自动选择 Pod 或获得 Pod 写权 |
| 该用户当时为 `join` | 允许 |
| `shared` 且用户在事件之后加入过 | 允许加入前历史；未设置或未知值按规范使用 `shared` |
| `invited` 且用户当时为 `invite` | 允许 |
| 其他情况 | 拒绝；`joined` 不授予加入前历史 |

成员与可见性变更事件的边界处理也遵循规范，不能简化为到达时间比较。补发、回填及客户端
读取均执行适用判定，并另行满足 Solid 授权。离房不意味着抹除已合法取得的历史副本；
撤销 Pod 访问权限则限制后续资源访问，不承诺收回已下载内容。

### 4.4 接收持久化、确认与投递恢复

每个逻辑 homeserver 明确一个**服务控制 Pod**，保存入站事务、可恢复事件、处理状态和
逐目的 Pod 的投递记录。它是具有明确服务主体及访问权限的 Solid Pod；不要求每个用户另建
控制 Pod，也不取代参与者自己的消息存储。资源 schema 归 models，SQL/Redis 只能作派生加速。
控制 Pod 的配置/发现方式与密钥托管须在实现前落实，不得静默回退到本地数据库。

1. 接收服务验证 Federation 请求身份及基本格式，以发送服务器和事务 ID 定位持久事务。
   重放恢复原事务响应；冲突载荷不能覆盖首次记录。
2. 在控制 Pod 保存可恢复载荷与处理意图，完成事件验证、补依赖或记录待处理状态。
   “收到”“等待依赖”“协议接受”“已投递”分别记录；未接受事件不得向客户端或 Agent 发布。
3. 按 Federation 端点语义持久保存事务响应及事件处理结果后才确认。HTTP 事务确认不表示
   每个 PDU 已接受，更不表示每个参与者 Pod 已落盘；尚需处理的载荷必须能从 Pod 恢复。
   控制 Pod 不可写时不能确认可恢复接收成功，必须返回可重试失败。
4. 对已接受事件生成可恢复的投递计划；逐目的 Pod 校验绑定版本、历史资格与服务写授权，
   写入协议事件、共享消息投影及发布事实。多资源写入使用存储契约的可恢复提交阶段。
5. 目的写入超时或服务崩溃后，按稳定 event_id 与提交记录核验原结果，再补齐缺失阶段。
   A 成功、B 失败只重试 B 的未完成阶段，不重发为新事件，也不重新触发独立执行。
6. 控制 Pod 的投递完成记录以目的 Pod 的持久提交证据为依据。正文已落盘但完成记录未写入
   时可恢复核验；资格或授权变化则重新判断，分别记录暂停或终止原因。
7. 只有投递完成或有明确终止处置后才回收暂存载荷；历史服务、事务重放及恢复所需材料须
   按各自保留契约继续保存。不得因网络响应成功而立即删除唯一副本。

控制 Pod 的接收/投递记录和目的 Pod 的消息/发布记录职责不同，不以跨 Pod 原子事务为前提。
仅有 event_id 清单不足以恢复丢失正文。客户端从自己的 Pod 提供增量，不复用服务器交易
或目的投递游标。服务控制 Pod 的恢复权限也不授予任意用户读取其他参与者事件的权限。

## 5. 三种同步的边界

| 层 | 职责 | 不可混淆的状态 |
| --- | --- | --- |
| 部署间同步 | 传输与验证事件、缺失事件获取、历史回填、状态解析 | 服务器交易/接收状态，不是客户端 since |
| 部署 → 参与者 Pod | 按资格与可见性持久化已接受事件，恢复部分成功投递 | 每个目的 Pod 的投递进度 |
| 客户端同步 | 从自己的 Pod 提供授权范围内增量与分页 | 客户端 token / 本地发布位置 |

## 6. 执行归属

- 消息复制与执行调度是**不同操作**；逻辑触发关联稳定的 `room_id` + 触发 `event_id` +
  目标 Agent + 用途，**不得**按各副本的 message URI 生成彼此独立的任务身份。
- 必须指定执行**归属方**与承载控制事实的 Pod；其他 Pod 复制执行事件**不获得执行权**。
- 多实例接替必须服从同一控制事实，不能靠互不共享的 Redis 租约或"各自看到 pending"抢占。
- Delivery/Run/RunStep 继续使用共享模型，并由 schema 明确区分"向某 Pod 投递消息"与
  "向 Agent 交付工作"；模型与 attempt 语义先在 models 定义。
- 执行仍至少一次；工具以稳定逻辑操作 ID 幂等。

## 7. 实现待办（目标不再待定）

| # | 决策 | 选项 | 影响 |
| --- | --- | --- | --- |
| D1 | 服务发现与绑定 | 稳定逻辑 server name、多实例路由、Pod 入口恢复与迁移版本 | 不将物理部署或 Pod 地址当作协议身份；多租户隔离须可验证 |

| D4 | Federation 兼容面 | 列明服务发现、请求认证、密钥、交易、加入/邀请、依赖与历史获取等端点及错误语义 | 对外遵循 Matrix Federation；内部 Pod 投递可有适配，不以自定义协议替代互通目标 |
| D5 | 旧数据迁移 | 旧随机 event_id 的房间与消息 | 不能通过开关变成合法 room v11 历史；保留兼容面或显式导入新房间 |

| D7 | 控制 Pod 运维与保留 | 启动入口、服务授权、容量、失败重试、备份和各类记录回收条件 | 不可写时拒绝不可恢复确认；清理不能破坏历史服务和重放语义 |

## 8. 验收草案（对齐设计文档门禁）

| 门禁 | 必须证明 |
| --- | --- |
| 身份映射 | 未证明 WebID 控制权不能绑定；哈希不能冒领远端 MXID；多 Pod 选择明确；迁移并发写可恢复且协议 ID 不变；不同设备可独立撤销 |
| 服务身份 | 多实例使用同一逻辑身份；路由地址迁移不改 server name；不同 server name 密钥隔离；轮换后旧事件仍可验证 |
| 事件身份 | 同一事件在两个服务/两个 Pod 中 event_id 一致；reference hash 使用固定测试向量，排除字段处理正确 |
| 签名与验证 | 缺失必需签名、伪造 sender、错误签名被拒；合法第三方转发通过；不能用 origin 替换 sender 验证；restricted join 附加签名受检 |
| redaction | unsigned 变化及合法 redaction 不导致误拒；内容 hash 不符时不发布原正文，按规范使用 redacted 副本；签名失败独立验收 |
| 确认与恢复 | 控制 Pod 不可写不确认成功；确认后立即崩溃可恢复；目的写成功但回执丢失不生成新事件；事务重放返回已持久响应 |
| 投递 | A 成功/B 失败后仅补齐未完成阶段；目的授权被撤销时暂停；恢复授权后按当前资格补发；暂存回收不丢唯一恢复材料 |
| 资格 | shared 可回填加入前历史；joined 拒绝加入前历史；invited/world_readable 及成员/可见性边界符合规范；邀请不授予 Pod 写权 |
| 授权 | 普通 PUT/PATCH 撤销或新增 Solid 授权后，新请求不命中旧 allow/deny；客户端读取与后台服务写入使用各自授权上下文 |
| 执行归属 | 副本不产生独立执行；接替服从同一控制事实；无有效接替授权时不得抢占 |
| 恢复与互通 | 清空本地派生状态后从控制 Pod 与参与者 Pod 恢复，不复活终态任务；两个独立服务真实互通，并与固定版本的独立 Matrix 实现核验兼容面 |

上述均为待执行门禁，历史单 Pod 测试不能作为通过证据。

## 9. 本草案不覆盖
