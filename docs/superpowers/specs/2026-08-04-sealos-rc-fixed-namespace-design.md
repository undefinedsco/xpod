# Sealos RC in a fixed namespace

## Context

Sealos issues one kubeconfig and one writable namespace for the selected data
center. The current CO kubeconfig defaults to `ns-1yl0rye9`. It can create
Deployments, Services, Secrets, and Ingresses there, but it cannot create those
resources or RoleBindings in `xpod-rc`. Therefore namespace-per-environment is
not an available isolation boundary.

## Decision

RC runs in the Sealos-assigned namespace alongside production, with complete
resource-name and data-plane isolation. The kubeconfig is a data-center-level
organization secret selected for the Xpod repository. `SEALOS_NAMESPACE`
continues to identify the assigned namespace and must never be assumed to be
`xpod-rc`.

RC owns these Kubernetes resources:

- `Deployment/xpod-rc`
- `Service/xpod-rc`
- `ConfigMap/xpod-rc-config`
- runtime Secret `xpod-rc-secret`
- seed Secret `xpod-rc-seed`
- three RC Ingress resources for identity, Pod storage, and API traffic
- their TLS Secrets, issued after Ingress creation by the Sealos certificate
  controller

Production resources such as `Service/xpod` and `Deployment/xpod-cloud` are
never selected, patched, or replaced by the RC workflow. The existing
`Deployment/Service xpod-inngest` is a shared data-center service and is reused
by both Xpod instances.

## Internal routing

RC uses its own Xpod service name:

- RC Xpod calls the shared Inngest at `http://xpod-inngest:8288`.
- The shared Inngest polls both `http://xpod/api/inngest` and
  `http://xpod-rc/api/inngest`; `--sdk-url` is a repeatable CLI option.
- RC sets `XPOD_INNGEST_SOURCE=rc`; production uses the stable default
  `production`.
- The source participates in the Inngest app ID, function ID, event names, and
  event payload. It is an origin marker, not an Inngest namespace or
  environment abstraction.
- RC app/function/event identities cannot overwrite or trigger production
  identities even though both use the same Inngest service and keys.
- RC does not bypass the data center's unified Nginx Gateway. Its Ingresses
  route `id-rc.undefineds.co`, `pods-rc.undefineds.co`, and
  `api-rc.undefineds.co` to the existing Gateway service. Nginx dispatches all
  three hosts to `Service/xpod-rc`.
- RC sets `CSS_BASE_URL=https://id-rc.undefineds.co` and allows exactly the
  three RC hosts. This mirrors the production identity, Pod storage, and API
  entry points without allowing production hosts.

The shared Inngest Deployment receives the second SDK URL as an additive,
stable configuration change. The candidate workflow verifies both URLs are
present before RC acceptance; it does not dynamically add/remove the URL or
scale/recreate the shared Inngest service. When RC Xpod is scaled to zero, the
poller may report that the RC endpoint is unavailable, but production app
registration and execution remain unchanged.

Selectors and pod labels use `app: xpod-rc`, so the RC Service cannot select
production pods.

## Shared and isolated infrastructure

RC reuses the data center's physical PostgreSQL, Redis, MinIO, Inngest,
ingress controller, and Kubernetes cluster. Its `APP_ENV_FILE` must still select an
independent PostgreSQL logical database or schema, nonzero dedicated Redis DB,
and independent MinIO bucket. The candidate workflow rejects production domain
and production-equivalent data values before deployment.

The RC seed is mounted from `xpod-rc-seed`; Alice and Bob are generated by the
RC runtime and used only for browser OIDC acceptance. Provider canaries are
cleaned up by the acceptance test.

## DNS, Gateway, and TLS lifecycle

Cloudflare provides DNS only. One DNS-only wildcard CNAME,
`*.undefineds.co`, points at the Sealos public ingress. Business routing is
owned by the unified Nginx Gateway, not Cloudflare.

The workflow validates that all three RC hosts resolve before publishing
candidate artifacts. It does not require TLS Secrets before deployment. After
applying the RC Ingresses, it waits for their Secrets, verifies that the
certificates cover the corresponding hosts, and only then runs public and
authenticated acceptance.

This matches the live Sealos pattern: an Ingress names its TLS Secret and the
Sealos certificate controller creates that Secret after the Ingress exists.

## Failure handling

- Missing kubeconfig, invalid assigned namespace, or unresolved DNS stops the
  workflow before npm or image publication.
- Missing or invalid TLS after Ingress deployment stops acceptance and uploads
  Kubernetes diagnostics.
- Any rendered `Namespace` object, production resource name, production
  selector, or production internal service address is a test failure.
- Scale-to-zero affects only `xpod-rc`; the shared Inngest remains available to
  production.

## Verification

Manifest tests render both the placeholder overlay and a custom assigned
namespace, then assert exact object names, selectors, internal addresses,
source-specific Inngest identities, Gateway-backed Ingresses, RC host
configuration, and absence of Namespace resources. Workflow tests assert the
prepublish DNS/kubeconfig gate, post-deploy TLS gate, RC-only rollout/diagnostic/
scale targets, and no production resource mutations. The existing full build,
package tests, lite integration suite, full Docker integration suite, and real
browser OIDC RC acceptance remain release requirements. Browser acceptance
must discover the authenticated WebID's `solid:storage` target and perform
create/read/update/delete against the real RC Pod, in addition to checking the
OIDC issuer and authenticated API entry point.
