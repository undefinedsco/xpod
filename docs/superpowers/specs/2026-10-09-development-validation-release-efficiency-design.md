# Xpod 开发验证与发布效率调整

日期：2026-10-09。

## 目标与授权范围

用户要求缩短每次开发修改的周转，减少重复测试和不必要的编译，并由 Xpod Remote 新会话执行。本文是本轮实施 spec；[流程复盘](../../testing/2026-10-09-development-release-retrospective.md)提供时间证据和原因分析。

交付包括开发验证入口、规则与回执、CI/发布依赖调整、只读环境预检和回归证据。实施分支基于最新 staging，最终提交到 staging 的 PR。此次不创建新版本、stable tag 或生产部署，不重新发布 0.4.30。若远端项目工作树有他人修改，保留原状态并在独立 checkout/worktree 实施。

## 保持的发布契约

- 开发分支普通 merge 到 staging，新的 exact staging SHA 接受独立 RC；通过后 squash 同步 main，核对代码树一致，stable tag 指向 accepted staging SHA。
- 容器按 accepted digest 提升，禁止重新构建后冒充已验收镜像。
- 本地 full 桌面验收使用实际安装的 DMG，对应 ZIP 内容一致；源码启动和最短探针不能代替它。
- RC 与 stable ZIP 字节不同，stable 的权限操作、自更新和消费者门禁继续执行；最终发布等待全部必需检查。
- Pod 读写、Gateway 认证、models、真实 Chat 分项证明；跨 WebID/Pod、安全隔离、会话恢复与切换的断言不删除。
- 原生产物复用仍校验输入、工具链、归档与 manifest 摘要，并执行新的原生 smoke。
- 共享 RC 整轮独占、所有权校验与清理保留；没有凭据或真实环境时，不把 fixture 写成实际环境通过。

权威发布规则仍归 [RELEASE.md](../../RELEASE.md)。实施时同步其冲突条款及 AGENTS.md，避免建立第二套长期规则。

## 改造一 开发验证按影响执行

优先复用已有构建与测试入口。需要统一入口时只新增一个轻量协调入口，不重写 runner，不添加依赖。区分 `quick`、`frozen`、实际安装验收和正式 RC；“quick 通过”不能输出发行通过凭证。

| 修改范围 | quick 必需执行 | 不应默认执行 |
| --- | --- | --- |
| 普通文档 | 链接、格式；涉及流程契约时运行对应现有文档/脚本契约测试 | 产品编译、完整集成、DMG、RC |
| 文案与样式 | UI 开发构建/热更新和受影响页面检查 | 后端、全部共享包、原生重编、完整集成、DMG |
| 前端逻辑 | 受影响 UI 与共享依赖的类型/构建、对应状态与交互回归 | 无关后端/原生重编、整套业务安装验收 |
| 后端局部逻辑 | 后端类型检查/相关构建、对应单元或集成用例 | 无关 UI 和原生重编、DMG |
| SDK、Bun 单文件、Electron 或原生边界 | 真实受影响的 compiled bootstrap/IPC/ABI 启动探针及定向回归 | 为了复现加载问题先走完整 DMG 与 Chat/Task 链路 |
| 验收脚本或 workflow | 相关 Node/Vitest/驱动契约、YAML/Action 校验；需要时运行真实子阶段 | 重建未变的产品、无关完整产品集成 |
| 权限、存储、跨模块公共契约或影响不明确 | 覆盖受影响消费者；影响面广时提前完整集成 | 根据文件扩展名猜测是小修改并跳过安全回归 |

影响选择须考虑依赖闭包和公共配置/lock 的变化。无法确定时回到保守范围；允许人工明确选择更广验证，并显示选择理由。不能仅靠 paths filter 保证安全。

失败先回到最小复现，修复后重跑该测试与受影响范围。不是每改一个断言、文案或驱动定位器就启动一次完整 RC。程序行为修复保留先 RED 后 GREEN 的证据。

## 改造二 冻结门禁只执行一次

将 AGENTS.md 及相关文档中“修复后完整集成”和“提交前再次完整集成”的机械双跑调整为：

1. 每次修改按影响执行 quick；广泛变更可提前执行完整回归。
2. 准备提交/本地 full 时，冻结本轮产品、测试、驱动、构建与配置输入，完成一次约定的完整回归。
3. 提交前核对冻结输入和环境未变化，复用该次有效回执，不再次执行相同命令。
4. 相关输入或环境变化、上一轮失败/取消/未完成、产物不匹配时回执失效；只补跑真正失效的验证组。无法判定影响时完整重验。

本地与 CI、不同 OS/运行时、源码与实际安装包是不同验证环境，不能以“命令相同”自动互相替代。新的 exact staging RC 仍运行当前必需门禁；此改造不修改 promotion 对 source SHA 的要求。

### 回执与安全边界

回执版本化，至少包含验证组、命令、开始/结束时间、退出状态、失败/跳过摘要，以及输入指纹：源码/测试/驱动/构建配置、依赖 lock 与补丁、相关工作区源码、工具链、平台、夹具与环境身份。产物验证还须绑定版本、归档摘要与 size。

指纹须覆盖影响构建的未提交及未跟踪非忽略源码；不得扫描或保存 `.env` 内容、凭据、用户数据和不相关目录。环境身份可记录非敏感标识，不能把 Secret 值写入回执。依赖闭包不能可靠推导时使用更广输入集合。

缓存回执仅用于已受控入口生成的开发验证复用，读取时重新校验输入和状态。任意用户 JSON 或旧回执不能作为跳过正式 CI/RC 门禁的凭证。有效成功、失败、阻塞、取消与未开始分别表示；历史事件与唯一当前摘要分开，不让旧 `running/pending` 覆盖终态。实现保持轻量，不建立新的验收平台或数据库。

## 改造三 桌面构建与验收分离

调整 candidate/release workflow 的依赖图，而非取消桌面检查：

- RC 包构建等待 metadata 与 exact native artifact，与服务镜像/部署并行；安装权限验收继续等待服务验收和包构建成功。
- stable 包构建在 promotion guard 通过后启动，可与 npm 传播和生产提升并行；实际权限操作仍等待目标生产实例通过。
- 每轮只构建一次该版本的 DMG/ZIP，上传不可变 artifact。下游下载该 artifact，通过 SHA、版本、ZIP/DMG 内容和摘要核验；不在验收 job 再构建。
- 将原 job 的消费者、真实安装、权限操作、自更新和组合验证明确分配到新 job，保留所有 required checks。
- Finalize、GitHub Release、失败摘要上传、RC cleanup 的 needs/always 路径覆盖新 job；生产/RC 锁不因拆分提前释放，也不形成嵌套锁死锁。
- 构建阶段不领取不需要的部署或用户验收凭据。重跑失败验收可复用本轮成功包，缺包、过期或摘要不同则失败，不能借另一版本的包。

## 改造四 发布前只读预检

在 npm publish、dist-tag 变更、生产镜像提升等写操作之前验证本轮生产与桌面验收的外部前提。保持现有发布权限，不自动修改 GitHub Environment、Secret、RBAC 或生产 Deployment。

- 检查预期 ref/tag 对实际 GitHub Environment 的许可和必要配置存在性；不能假设 workflow 文件中的 environment 名称就代表服务端已允许。
- 检查生产实际 service container、启动参数、Secret/ConfigMap 引用及键存在性/必要非空状态。无需读取的 Secret 不读取；检查返回只给名称和通过/失败，不给值。
- 检查既有发布目标/namespace、数据库/路由配置边界，旧版更新 archive、accepted native artifact 的可获取性及摘要。
- 缺权限或不可访问时明确失败/阻塞；不吞错误、不以 mock 代替实际预检、不为绕过预检扩大访问权限。
- rollout 出现确定的配置错误时提前输出固定原因。Transient Pending、短暂拉取延迟不能单凭一次观测判死；仍保持有界等待及实际新 Pod/digest/健康门禁。
- rollback 分别记录“请求已应用”和“readiness 已确认”，旧 Pod 健康不能替代新 Pod 启动证明。

若当前 `rc` Environment 不适合 stable 桌面验收，可实现明确的 Environment 配置入口及文档，记录运维准备事项；新会话不自动关闭保护或添加宽泛 tag 通配许可。配置权限不足的外部事项单列，不能宣称整体已落地。

## 改造五 编译复用与耗时观测

QLever 完整缓存已经命中，18 秒 job 是本轮基线；保留现有机制，不另造缓存或重复冷编译。对源码、工具链、原生 ABI、缓存输入变化验证失效行为。

统计共享包和 UI/后端构建的实际执行次数及冷/暖耗时，先消除同一 job/工作区里无变化的重复调用。共享包按依赖闭包构建；并行仅用于确实独立的包。跨 job 复用仅在输入、lock、平台和工具链相符且摘要可核验时启用；不要共享可被并发写入的 `node_modules` 或可变 dist。

如果跨 job artifact 的传输成本没有实测优势，不强行新增这层缓存，交付测量结果与判断即可。已发布共享版本复用继续遵守现有 tarball/provenance 契约，不能覆盖同版本。

npm 等待保留 metadata、实际 tarball 下载与 SRI 校验；有界退避和完成事件减少请求/Agent 唤醒，不能将公网传播等待写成编译耗时或盲目重复 publish。仅重试失败下游，不删除/重打 stable tag。

## 验收与交付

必须验证以下行为，优先扩展现有测试和 helper，不用只检查新实现文本的镜像测试：

1. 文档、UI、后端、验收脚本、广泛公共变更五类选择的执行范围正确；未知影响保守处理，公共依赖变化包含下游。
2. 同一冻结输入成功回执可复用，源码/测试/驱动/lock/工具链/环境变化会失效；失败、取消、不完整或伪造凭证不能通过。
3. 同一冻结候选完整集成只执行一次；提交前只校验回执。最终一次完整集成真实输出保留通过和跳过原因，不在交付前无变化地再跑一遍。
4. compiled loader、Task signal、WebID 切换和跨 Pod 拒绝等已有回归继续通过；新协调入口没有把它们静默排除。
5. 两条 workflow 的依赖图允许先构建包，但禁止提前权限验收/Finalize/Release/cleanup。失败构建、缺 artifact、摘要或版本不匹配、验收失败均无法晋级。
6. 缺 Secret 键、tag 规则不允许、无读权限、坏配置的 fixture 正确失败，日志不泄漏值；可访问的真实预检单独给证据。
7. YAML/Action、相关 Node/Vitest、生产和测试类型检查、lint 按改动适用范围通过；完整集成最后执行一次；影响到安装链路时用实际安装包验证。
8. 给出本机 quick、冻结门禁、构建的命令与耗时，以及 CI job 拆分前后关键路径分析。实测与估算分开，不承诺没有运行过的提速比例。

最终提供：修改文件、规则简化、有效验证回执、必须外部准备的事项、剩余风险与 staging PR。不得把“脚本写完”或“单元通过”写成真实 RC/生产已经通过。正常实现范围内持续完成；确定外部权限阻塞时提交可审查的结果和具体阻塞，不反复运行同一无效长链路。
