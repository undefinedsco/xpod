# Fabric 远程 Workspace 需求

日期：2026-10-07
状态：当前需求基线；尚待技术设计与实现核对；MVP 验收 **NOT RUN**。

本文整理原始 Fabric 需求及同一会话中用户的后续修正，只规定目标、职责和可观察结果，不确定 API、传输协议、数据库字段或进程管理实现。文档完成不代表 Fabric 已完成或已通过验收。

## 1. 来源与当前决定

| 原始需求 | 当前口径 |
| --- | --- |

| 第一阶段必须启动 Codex CLI | 已被替代：复用 Pi 的 Agent 执行能力；Codex CLI 不再是 MVP 必选依赖 |

已确定的职责划分：

- **Pi** 负责 Agent 执行。
- **LinX** 负责 Chat UI。
- **Fabric** 负责 Node / Workspace 关联、远程路由、受控服务预览，以及断线后恢复访问所需的衔接。
- **Thread / Run** 继续承载既有会话与执行语义。Fabric 需要关联这些对象，不复制第二套会话、任务状态或生命周期权威。

以上是用户确定的职责约束，不是本次对源码或部署状态的核验结论。设计前仍需核对既有能力和缺口。共享定义及运行边界遵守[仓库原则](../../../AGENTS.md)；通用平台背景参见 [Pod-native Applet Platform Architecture](2026-08-12-pod-native-applet-platform-architecture.md)，其中较早的探索项不能覆盖本节用户修正。

## 2. 目标与用户场景

用户把 Mac mini、工作站或服务器作为长期在线的计算节点，从 MacBook、浏览器或其他客户端通过 Chat 使用节点上的开发 Workspace。代码、依赖、构建、测试及本地服务留在 Node 执行；客户端主要负责身份认证、选择工作环境、交互和查看结果。

典型流程：

1. 用户将自己的 Mac mini 注册或关联为可访问 Node。
2. 用户在 LinX 选择该 Node 上已有的 Workspace，或创建、绑定一个有权使用的目录。
3. 用户在 Chat 中提交任务，复用既有 Thread / Run，由 Pi 在选定 Workspace 中执行。
4. 用户查看执行进展、结果和可用的服务预览，并通过既有交互能力继续任务或请求中断。
5. MacBook 合盖或网络断开，Node 上已开始的任务继续执行。
6. 用户重新连接，回到原 Thread，查看同一 Run 的真实状态、已有输出和结果，继续后续交互。

MVP 应验证上述闭环。会话迁移到 Mac mini、SSH 连通或 Codex 官方 Handoff 成功，均不能替代 Fabric 产品闭环的验收。

## 3. Node 与长期 Workspace

### 3.1 Node

Node 是实际执行计算的设备，必须明确所属用户或授权关系。用户应能识别当前执行目标、可达情况及与本次任务有关的能力；基本资源和负载信息用于帮助选择，不引入复杂调度要求。

节点离线时，保留其 Workspace 关联信息，并明确显示暂不可访问。节点重新可达后，用户应能再次访问原有 Workspace。不得因节点暂时不可达而自动将任务切换到客户端或另一台机器。

### 3.2 Workspace

Workspace 是 Node 上长期存在的工作目录和执行环境，生命周期独立于客户端连接和单次 Run。

用户应能：

- 查看有权访问的 Workspace、所属 Node 和足以辨认项目的仓库或目录信息。
- 创建 Workspace 或绑定已有目录，并进入该工作环境。
- 多次连接同一 Workspace，保留代码、依赖缓存、构建产物和所需开发环境。
- 关联、查看该 Workspace 的既有 Thread / Run 及已授权的服务预览。
- 使用不同仓库或同一仓库的独立 Git worktree 开展并发工作，避免把不同工作目录混为同一个执行目标。

MVP 不要求 Fabric 自动创建 Git worktree。绑定目录不等于获得整个 Node 文件系统的访问权；可操作路径必须受相应授权约束。

### 3.3 并发任务

多个 Thread / Run 可以关联同一 Node 上的不同 Workspace，或明确区分的工作目录。用户必须能判断每项任务的实际执行位置，输出和控制操作不能串到其他任务。

任务启动、取消、完成和失败等语义由既有执行体系定义。Fabric 只补远程关联与路由；如现有能力不足，先记录集成缺口，不以新建平行 Agent Session 系统解决。

## 4. 远程连接与断线恢复

### 4.1 网络要求

- 外网客户端应能访问家庭网络内的授权 Node，无需用户拥有公网 IP、暴露 SSH 22 端口或手工配置路由器端口映射。
- Cluster 可以承担节点发现、身份与授权协调及连接协调；主要工作数据流应优先在 Client 与 Node 之间直连。
- 不把所有 Workspace 数据流默认集中到 Cluster，也不把 Cloudflare 等特定中心化代理作为必需前提。
- 具体直连技术、是否允许中继及中继授权策略留待设计；尚未选定具体协议，也不承诺任意网络条件下都可直连。

### 4.2 客户端断开

客户端关闭、合盖或短暂断网，不应仅因交互连接消失而终止 Node 上已开始的 Run 或本地服务。依赖用户输入或授权的任务应遵守既有执行规则，不能因为用户离线而越过等待步骤。

恢复连接后，用户应看到同一 Workspace、Thread 和 Run，能够区分正在运行、已经完成、失败或仍不可确认的情况，并查看断线期间产生的可恢复输出和结果。恢复访问不得隐式重发任务、生成重复 Run 或重复执行有副作用的操作。

上述要求适用于 Node 仍正常运行的客户端断线场景。Node 断电、重启、Pi 进程退出后的任务恢复能力是待设计问题，不能与客户端重连恢复混为一谈。

## 5. 身份、权限与服务预览

用户必须经过相应的 Xpod 身份认证和授权检查，才能发现或访问受保护的 Node / Workspace。认证成功不自动赋予机器控制权、任意目录访问权或所有 Run 的操作权；实现应复用既有身份与权限权威，不另造通用超级会话。

远程执行和中断等控制操作必须作用于用户有权操作的目标。匿名或未获授权的调用不得访问受保护的执行内容；切换用户或目标后不能沿用上一对象的权限。

Workspace 内启动的开发服务可以提供受控预览，例如前端页面或 API。要求：

- 用户能够辨认预览来自哪个 Node、Workspace 和服务。
- 服务默认不公开到 Internet，仅授权用户可访问。
- 只开放已选定并获授权的服务，不因一个预览入口而获得 Node 任意端口的访问权。
- 服务停止、Node 不可达或预览授权失效时，明确反馈当前不可用状态。
- 关闭或撤销预览访问后，原访问入口不再允许新的未授权访问；已有连接和运行中任务如何处理需在设计中明确。

服务进程、Run 和预览访问许可可以具有不同生命周期；客户端关闭不应被直接解释为杀死服务。其关联、关闭和回收策略需形成可验证的契约。

## 6. 非目标与后续范围

本阶段不建设完整 IDE、在线文件编辑器、VS Code 克隆、云端代码同步、云端文件系统、复杂计费、Kubernetes / GPU 集群调度、分布式编译或完整 CI/CD 平台。

PTY、终端 UI、必选 Codex CLI、新的 Agent Provider 注册体系和第二套 Agent 生命周期系统不属于当前 MVP。节点重启后的自动续跑、跨节点迁移、Workspace 快照、Git / worktree 自动化及复杂多 Agent 编排，需后续独立确定范围。

## 8. 设计前需要解决的问题

1. 现有 Node / Workspace、Thread / Run 的权威来源是什么，如何关联且保持唯一状态来源？哪些能力已存在，哪些需补齐？
2. LinX、Fabric 与 Pi 各自承担哪些远程调用、事件订阅和错误反馈？现有 Thread / Run 契约需要怎样的最小扩展？
3. Workspace 目录绑定、并发 worktree、路径边界和权限撤销如何执行？Node 授权、Workspace 授权与 Run 控制权如何衔接？
4. 断线期间输出如何保留、补取和去重？恢复请求如何避免重发任务？无法确认状态时如何呈现和核对？
5. Node 重启或执行进程退出后保留什么状态？哪些任务可恢复、哪些只能报告中断？不得先承诺透明续跑。
6. 直连与可选中继采用什么策略，如何观测真实路径并验证“不默认全量经过 Cluster”？
7. 服务预览支持哪些服务类型，如何确定访问范围、授权期限、关闭行为和已有连接的撤销效果？

后续实现设计需逐项回答并映射到验收编号。本次未核对源码实现、未运行产品测试，也未确定这些问题的技术答案。
