# Xpod 功能、操作与信息架构审查

日期：2026-09-27 · 证据层：设计文档。未读取产品实现、未运行界面；以下是设计判断，不是实机缺陷或用户测试结果。

## 1. 对上一轮结论的修正

上一轮主要完成规范冲突校正。它将五工作区、固定三栏、Status 默认结构作为前提，再补上颜色、状态和验收，**没有充分审查这些结构是否适合用户任务**。“规范一致”不能替代“功能与布局成立”。

用户明确过产品源头、北极星、LinX/Xpod 关系、品牌选择，以及按设计文档审查的方式。在本轮已读材料中，五工作区、64px 图标 Rail、232px 永久 List、18 项 Status 导航是继承的设计选择，不能升级为不可改的用户决定。

本次按任务重新判断这些选择，结论回写[实施 spec R2](superpowers/specs/2026-09-27-xpod-product-experience-spec.md)。上一轮全文见 [R1 历史快照](design-history/product-experience-r1-2026-09-27.md)，其中的结构锁定已失效。认证权限、显式副作用、资料所有权和既有品牌决定继续有效。

## 2. 主要设计问题与裁决

证据引用 R1 固定快照的章节，避免后续纠正文档后找不到原问题；对应的原始设计来自 8/9 Shell 和 AI Connections。操作链是根据文档推导，不是实测点击次数。

| ID / 判断 | 文档证据 | 为什么不成立 | 本次裁决 |
|---|---|---|---|
| UX-01 · 18 项 Status 常驻导航应收回 | R1 §3.1、§7.1；原 Shell §5 将概览、三服务、日志、八项索引、五项用量并列 | 用户为“连不上、搜不到、空间满”先学内部分类；18×44px 已占792px，800px窗口还没计标题与分组就要滚动导航 | 概览直接内容页；服务、用量、搜索与索引各有聚合详情；RDF/FTS/Vector、缓存、慢查询、Benchmark 下沉专业诊断，保留直接地址 |
| UX-02 · 全产品固定三栏没有任务依据 | R1 §3.1、§8.3 强制64+232+Content，中屏必须先列表后详情 | 日志、单机概览、自启动表单没有需要比较的对象集合，永久中栏浪费宽度并增加一次选择；两个AI图标靠tooltip辨认 | 基础为文字导航+内容；仅真正对象集合启用列表—详情；诊断页给足内容宽度 |
| UX-03 · Network 八页拆散一次连接任务 | R1 §7.2；原 Shell §6 的 Endpoints/Addresses/DNS/HTTPS/Tunnel/P2P | “让另一台设备连上”被拆成技术名词，用户自行拼接地址、域名、证书和隧道 | 服务与访问内提供“访问与连接”“对外访问设置”“诊断”；按本机/局域网/外部范围给地址；技术端点放开发者连接信息 |
| UX-04 · 存储管理埋在设置，而用量与索引散在别处 | R1 §7.1、§7.4、§7.5 | 创建空间、知道位置、查看访问、解释占用都是产品核心任务，用户却须在Settings/Pod/Storage/Status/AIConfig猜入口 | “存储空间”直接进入已有Pod管理body；空间详情聚合位置、用量、访问及搜索处理；各区域仍单独验证权限 |
| UX-05 · 两个AI一级入口暴露了内部职责 | R1 D-01、§7.3/7.4；原AI规范以API Keys和Provider目录开场 | “连接Codex”“为资料选择AI”被迫先理解连接与配置两个模块；全量服务商目录占据未使用产品的注意力 | 一级整合为AI；以任务和已配置对象开场，添加时才出现目录；领域实现仍各自负责 |
| UX-06 · 创建密钥被当作客户端接入起点 | R1 §7.3；AI原创建表单主动作Create and apply | 有现成key仍容易新建；key成功、写文件失败后重试范围不明确；Gateway可用不等于客户端已采用配置 | 先选客户端和模型，明确复用/隔离凭据，预览后提交；分阶段记录，重试仅失败步骤，不重复建key |
| UX-07 · 模型勾选包含隐藏执行语义 | 原AI规范“第一个已选embedding模型成为默认”；R1未消除此规则 | 勾选目录/调整顺序可能改变执行模型和索引范围；用户无法从当前用途预测生效值 | 分开发现结果、允许列表与用途模型；排序不决定默认，生效来源必须明确。是产品行为目标，运行侧适配列为独立依赖 |
| UX-08 · 四个AI配置主题拆散一次模型改变 | R1 §7.4 的Assignments/Processing/Search/Lifecycle | 保存、重建虽然分开，但资料去向、延后重建的搜索影响仍由用户拼接 | 按识别文字、理解文档、按意思搜索等真实用途组织；同一任务内选模型、看影响、决定保存/重建、看结果 |
| UX-09 · 正常首页和托盘过度强调后台进程 | R1 §7.1先三服务后地址和异常，§9.2托盘再复制服务与五工作区 | 表达为“需要你照看系统”；更换暖色不改变这种感觉；可选能力未配置容易成为长期催促 | 正常呈现精确结论、实际使用入口与位置；异常按影响前置；服务正常收成摘要，异常再展开；托盘只保留当前判断与必要动作 |
| UX-10 · 参数一致掩盖了信息平权 | R1 §8.2全体44px，§8.3五底Tab；用途行字段/动作并列 | 设置墙与诊断表需要不同密度；大按钮、徽章、边框到处平权；640×560又被底Tab占用高度 | 公共密度按精确/粗指针区分；对象行只保留名称、主描述和关键状态；窄屏用任务栏+导航抽屉，不强制移动五Tab |

## 3. 重新安排功能，而不只移动菜单

| 功能/设计 | 处理 | 可实施边界 |
|---|---|---|
| 概览 | 保留并重做优先级 | 新窗口默认落点仍可承担总体判断；首次、正常、停止、未知、异常分别有正确主动作；唤回窗口保持当前任务 |
| 三服务、索引细项、日志、Benchmark | 从日常导航降级 | 有稳定直达入口；日志宽内容；Benchmark无自动执行、无伪造实时曲线 |
| Network 独立一级与八个平行页 | 合并 | 服务与访问内按连接任务组织，配置和观测可同页但分区；不修改规范身份地址 |
| Pod / Storage / Usage / Index 的相关呈现 | 按空间聚合 | 同一事实只保留一个owner，复用视图；聚合不合并权限，不要求所有区域先登录同一会话 |
| AI Connections / AI Config 一级分离 | 合并入口 | 客户端、连接、用途、访问密钥仍是不同对象；不融合数据模型或凭据 |
| 全量Provider目录 | 改为添加过程 | 日常显示已连接对象；不支持的provider不制造常驻假入口 |
| API Key 管理 | 保留专业入口 | 任务内按需复用/创建；停用前说明已知客户端及用途影响，也说明未记录关联的局限 |
| OCR/Reader/Embedding等模型角色 | 按有意义用途和真实消费者显示 | 空泛角色不因为schema存在就必须占一行；专业名称在详情可见 |
| 后端选择、维度、队列参数 | 降级/只读/条件编辑 | 用户能作实际决定且部署支持安全生效才可编辑；不能把数据库迁移画成随手切下拉即完成 |
| 删除源资料后移除派生索引 | 作为一致性规则，不给普通用户“保留已删资料的搜索结果”开关 | 实施 owner 维持来源/权限一致；处理延迟应如实表达并避免让已删除或失权内容继续成为可访问结果 |
| 更新后同步索引、自动处理 | 只暴露有意义的策略 | 用户可以决定是否处理、何时处理、处理范围；不暴露会破坏状态可信性的内部一致性开关 |
| Open Pod | 按真实能力命名 | 有已支持的内容应用才写“查看资料”；只有资源URL时写“复制存储地址/打开存储地址（开发者）”，不假设存在网盘界面 |
| 全局设置/Cloud独立页 | 按内容重归属 | 账号归身份入口，启动/部署关系归服务，位置/权限归空间；没有实际应用偏好就不补空设置页 |

## 4. 推荐信息架构与布局

这是本次设计判断并已写入R2，尚未做真实界面可用性验证，不假称用户曾逐项确认。

    Xpod                         当前页面明确显示自己的机器或空间范围
    概览                         结论、影响、入口、位置
    存储空间                     Pod清单 → 当前空间、用量、访问、搜索处理
    AI                           连接客户端 / 资料处理；已连接服务和管理入口
    服务与访问                   服务与启动 / 访问与连接 / 对外访问 / 诊断
    管理账号                     独立身份入口，Account与WebID分开说明

四个入口服务于可识别的任务域；不是以“图标数量少一个”为收益。服务与访问是桌面正式能力，专业用户可以直达；不将其藏在难以发现的高级菜单。云端若没有机器管理能力，则不暗示可控制主机，按实际支持呈现访问详情。

基础布局是184px文字导航+内容。只有Pod、服务连接等多个同类对象需要持续比较/切换时，宽窗才出现224px对象列；概览、固定设置、日志没有被凑出来的中栏。窄窗复用同一导航树，当前任务优先。

## 5. 中间操作必须这样连起来

| 任务 | 旧文档推导的路径 | R2目标路径 | 保留的真实决定 |
|---|---|---|---|
| 首次连接客户端 | Provider → 模型 → API Keys → 创建/应用；缺Pod再找Settings | 连接客户端 → 选择可用连接/模型 → 必要时在原任务上下文完成账号与空间准备 → 明确复用/创建key → 配置预览 → 应用/复制 → 分层验证 | 保存位置、授权、模型、凭据隔离、配置覆盖；不为内部查询增加“下一步” |
| 改语义搜索模型 | AI Config数页 → 重建 → Status索引 | 当前空间的搜索处理 → 模型与影响 → 保存/安排重建 → 原处看状态 | 资料范围、外发、成本未知或实测估计、何时重建；延后可能只剩文本检索需明确 |
| 另一台设备连接 | Overview/Endpoints/Addresses/DNS/HTTPS/Tunnel来回 | 访问与连接 → 选访问范围 → 当前可用地址；确需配置时进入该方式的设置 → 在原任务检测 | 公网暴露/所选访问方式/必要凭据；不因进入页面自动开放网络 |
| 上游连接失效 | 找密钥或provider对象 → 重连 → 自己回原应用确认 | 原客户端/用途显示影响 → 修复该连接 → 重读原模型状态 → 有权限且无新增费用的检查 → 回原任务 | 重新授权或有费用测试才需明确动作；不顺带换Pod/重建key |
| 建立自己的空间 | 注册 → 管理页 → 找Pod页面 → 创建 → 找回授权 | 注册只建Account；已发起任务保留标题与“继续准备空间”入口 → 明确位置与创建 → 必要授权 → 回原任务 | 不自动创建，不把绑定存在当作真实资源就绪，不绕过Account/WebID各自权限 |

这些是连续任务，不要求做一套新通用向导。复用现有body/controller，只把用户必须作决定的节点显示成步骤；读取、校验、发现等内部阶段提供反馈，不要求用户逐个确认。

## 6. 气质如何落到操作，而不止是色板

- **安静**：正常状态不堆健康勾、仪表盘卡或持续催促；没有配置可选AI/公网不当作系统异常。
- **能干**：用户说清任务后，系统负责读取已有配置、展示兼容选项、保留阶段结果；失败指出唯一需要恢复的步骤。
- **由用户掌握**：决定发生在保存位置、授权、覆盖配置、外发处理、有成本重建等实际后果前；不是对每个内部动作都问一次。
- **可信**：结论附对象、范围与必要时间；资源未知就说未知；专业细节可展开与直达；少一次确认不能以隐式副作用换取。

正常概览首屏目标：一个精确结论、最多四组事实、零或一个强调动作。对象列表只显示名称、一个主描述、关键状态；配置只在有修改时强调保存；诊断以范围、筛选、证据为主。此处是待实施检验的信息预算，不是已做用户测试的测量结果。

## 7. 各路AI新增的自查责任

每个模块先回答，再检查token与像素：

1. 这项功能让谁作什么决定？删除这个入口后，哪条真实任务受损？只有内部名词而无任务的入口应合并或降级。
2. 用户从意图到结果必须作哪些决定？区分必要决定、系统可完成的检查、危险的隐式动作；给出完整前后链路。
3. 当前页型是否需要对象列表？静态章节和真实集合不得为了统一三栏混用。
4. 正常、首次、停止、异常的首屏分别回答什么？可选能力的缺失不能成为长期告警。
5. 每行信息与按钮是否具有同等重要性？读写语义分开不要求两个工作区，模块分工也不要求用户跨页。
6. 气质靠哪些可观察行为实现？不能只用“温暖、克制、高级”作验收结论。

审查结果须逐功能给出：**保留 / 合并 / 降级 / 条件显示 / 删除入口（保留底层能力）/ 待证实**。允许质疑现行设计本身，但不可自行放宽认证/数据保护规则，也不可修改用户明确选定的品牌。
