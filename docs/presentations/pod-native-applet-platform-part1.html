Part 1 · 从个人意图到可复用能力01

我们真正要做的不是另一个 AI 聊天框，也不是把所有功能塞进一个超级 App。目标是每个人自己的 Jarvis：用户表达意图，系统在他的 Pod、授权和偏好范围内发现已有能力，组合可用部分，只创造缺失部分，验证后运行。这里的“能力提高”不是让用户学会开发，而是通过 AI 和平台积累经过批准的映射、偏好、配方与证据。

这里必须先把产品形态说清楚：Jarvis 不是一个万能大模型，也不是一个不断膨胀的超级 App，而是一组围绕同一用户协作的 Applet。Files、Notes、Tasks、AI Connections 和自动化都可以独立演进，但共享 Pod、身份、权限和偏好。AI 按需求发现、组合和修改已有能力；需要新 Applet 时，由 Applet Factory 负责生成、验证和交付。

Jarvis 的功能没有自然上限：不同人的需求、数据和流程都不同，所以个性化必须是一等能力。但如果每个人和每个 AI 都从零生成，生态就不存在。我们的解法不是强迫所有功能完全一致，而是共享稳定边界，把差异放进用户 Pod、配置和可替换贡献中。

这也是为什么之前 AI Connections 很容易出现假按钮、重复 Session、登录框不一致、写入落错位置等问题。不是模型完全不会写，而是它被要求同时做产品、架构、身份、安全、语义和部署决策。平台应该把这些高风险判断变成可复用契约，让 AI 把注意力放回用户真正缺少的领域能力。

分层不是为了画架构图，而是为了减少错误空间。Models 管共享语义，drizzle-solid 管 ORM，Solid Runtime 管登录与 Pod 访问，Extension 层管扩展契约，Shared UI 提供公共原语，Linx/Host 管产品几何，Xpod 管可信能力与执行。Shopify 的生态表面、VS Code 的扩展契约、Workers 的能力绑定和 Replit Agent 的生成验证闭环分别提供了可参考的部分，但我们的权威数据长期留在用户 Pod。

分层以后，AI 的交付单元不必永远是完整 Applet。它可以只补一个 View、Command、Agent Tool、API Handler、Worker、Mapping 或 Protocol Adapter，再放进统一的 Extension Package 中获得身份、兼容、权限、测试和来源。Protocol Adapter 指 OpenAI Chat/Responses、Anthropic、ACP、MCP 等外部协议翻译，不是某个模型供应商的硬编码分支。

Discovery 是“大家一起来”的关键机制。它不只是一个发现页面，而是人和 Agent 在创造前的能力解析层：先找已有，再组合，只有确实缺失时才生成最小贡献，最后把描述、测试和来源回流。这样共建不是号召，而是默认工作流。

Applet Factory 是面向用户和 AI 的产品能力。它接收意图，先发现和组合已有能力，只生成领域差异，再接入真实数据和权限进行验收，最后形成可安装、可升级、可撤销的 Applet Package。它不是另一个聊天框，也不是内部多 Agent 调度器；它是 Jarvis 生态的 Applet 生产系统。

13 · The Next Problem

Applet 变简单
Factory 本身却不简单

the build question

我们已经把要建什么拆清楚；接下来要解决的是如何把它快速建出来。

Identity、Models、ORM、Shared UI、Host、Extension、Runtime、Discovery 与 Delivery 都需要真实实现和真实验收。

APPLET FACTORY面向用户和 AI 的产品生产能力。
TARGET APPLETS用目标需求和验收场景定义 Factory 缺口。
AI R&D PIPELINE用清晰任务、并发与验收放大团队吞吐。
EVIDENCE LEDGER证明是否真的更快、更稳、更便宜。
Applet Factory 是产品；AI 研发流水线是我们建设这个产品的方法，不能混成一个概念14

这里才进入“我们怎么建”的讨论。Applet Factory 是面向用户和 AI 的产品能力；内部 AI 研发流水线是 Undefineds 建设它的方法。前者要进入 Xpod/Linx 生态，后者可以先用 Codex、任务系统、Git worktree、CI 和现成编排器实现，不要求先把第二套产品塞进 Xpod。
