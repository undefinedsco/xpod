# Xpod 镜像边界

本文件约定服务镜像的交付范围。镜像内容以此为目标，当前打包偏差单列在文末，不能把约定当成已经完成的验收。

## 一个服务镜像，三种部署模式

Cloud、Local、Standalone 共用一个 Xpod 服务镜像。模式差异由启动配置、身份来源、存储后端和外部服务连接决定，不按模式重复构建、安装依赖或维护三套 Dockerfile。

- 同一版本、同一平台，三种模式使用同一个不可变 image digest；不同 tag 不算不同产物。
- 多架构发布可以有不同的平台 digest，但属于同一个版本的 OCI 镜像索引；不能将架构差异误称为模式差异。
- Standalone 是独立身份与存储的部署方式，不要求增加一套服务实现。当前验收栈使用 Local 配置入口，显式配置本站规范地址与本站 IdP。
- Local 可以连接 Cloud 提供的身份与节点服务，容器部署的 Local 仍使用同一个 Xpod 镜像，Pod 数据仍由绑定的 Local SP 托管。Cloud 服务依赖不等于镜像依赖。

配置决策遵循 [配置策略](CONFIG_STRATEGY.md)，实际三模式验收见 [运行模式矩阵](acceptance/runtime-mode-matrix.md)。

## 产物归属

| 内容 | 所属产物 / 位置 | 边界 |
| --- | --- | --- |
| Gateway、CSS、API | Xpod 服务镜像 | 一套编译产物与运行时依赖；进程分工不意味着三个镜像 |
| Account、App、Settings 等 Web 页面 | Xpod 服务镜像 | 带构建后的静态资源，与后端同版本；不需要 Vite 开发服务器 |
| Components.js 元数据、配置模板、内部 workspace 包 | Xpod 服务镜像 | 保留运行所需文件与包解析关系，不将整个开发 workspace 当成运行依赖 |
| Bun 与必要系统库 / 工具 | Xpod 服务镜像 | Bun 优先；仅保留实际运行需要的依赖 |
| TypeScript、测试框架、浏览器测试程序、打包器 | 构建 / 测试阶段 | 不进入最终服务镜像 |
| Electron、桌面打包器、桌面安装包 | 桌面产物 / 桌面构建阶段 | 不因共用 monorepo 就带进服务镜像；桌面壳消费服务产物 |
| PostgreSQL、Redis、MinIO 等 | 独立基础设施容器或外部服务 | Cloud 按部署需要连接；不嵌进 Xpod 服务镜像 |
| pgvector、PostgreSQL 侧原生 RDF / QLever 扩展 | 对应数据库镜像 / 扩展构建产物 | `.so` 在数据库侧加载，Xpod 通过 SQL 使用；不得因此向 Xpod 镜像加入 PostgreSQL 服务、CMake 或 QLever 编译工具链 |
| 账号、Pod、SQLite / PostgreSQL 数据、会话持久化、日志 | 运行时卷或外部存储 | 不烘焙进镜像，也不按构建缓存清理 |
| Provider 凭据、用户 API Key | 用户 Pod 的受保护资源 | 不写进镜像、构建参数或默认环境文件；部署凭据由运行环境注入 |

数据库扩展的构建与功能验收由对应扩展分支负责。本轮 Xpod 基础服务矩阵保持 QLever 关闭，不以扩展产物未完成为由阻断其余三模式验证，也不据此宣称 QLever 已通过。

## 构建依赖不等于运行依赖

多阶段构建允许构建阶段使用完整工具链，但最终 runtime 阶段只交付服务需要的产物和依赖闭包。`NODE_ENV=production` 不会自动删除之前复制进来的开发依赖。

- Gateway、CSS、API 的运行时选择统一处理，遵循 [Bun 运行时规则](bun-runtime.md)。`node:` 导入不等于需要安装 Node。
- Node ABI 或可选原生模块确实需要编译时，可以在构建阶段提供工具链；这与数据库侧 QLever 编译是两件事，不能据此扩大最终镜像边界。
- 可选 Agent / 终端能力所调用的 SDK、CLI 或原生模块，应按实际运行路径明确归类。不能仅因它目前列在 `devDependencies` 就删除，也不能以“可能会用”为由保留整套桌面和测试依赖。
- 依赖裁剪前先锁定运行行为，检查动态加载、workspace 链接、Components.js 元数据和已发布能力；禁止直接整目录删除后只用启动成功证明没有回归。
- 单文件可执行包是另一种分发形式，不是 Docker 服务运行的前提。是否构建单文件，不改变本文件的模式与数据库边界。

## 空间统计与开发迭代

三种模式各开一个容器时，共享同一镜像的只读层；分别增加的是容器可写层和数据卷，不是复制三份镜像。

排查空间时分别统计最终镜像、构建缓存、容器可写层和数据卷；压缩层、解压层与共享层的数字不能直接相加。不要用“要验收三种模式”解释开发依赖或旧构建缓存的占用。

- 日常修改优先复用构建缓存。服务代码调试可用 `docker-compose.acceptance.dev.yml`，让三种模式只读挂载同一份编译产物和锁定的依赖补丁。
- 上述挂载只用于快速回归，不构成不可变镜像的发布证据。收口时移除 override，构建一次，再用同一 digest 跑完整三模式矩阵。
- 仅清理已确认可重建、属于当前任务的旧缓存；保留账号、Pod、数据库卷。具体操作见 [构建问题排查](docker-build-troubleshooting.md)。

## 当前偏差与收口要求

2026-08-28 检查当前 Dockerfile 和本地验收镜像发现：

1. 三种模式已引用同一镜像，并不是各自打包一份。
2. 构建阶段安装了完整开发依赖，runtime 又整体复制 `/app/node_modules`。其中包含 Electron、桌面打包器及测试工具，违反上述服务镜像边界。
3. 当次检查的 `/app/node_modules` 约 2.1 GB，Docker 构建缓存约 5.6 GB；这些是环境快照，不是镜像容量目标，也不是三模式各自占用。
4. 部分实际运行时使用的 Agent / 终端依赖仍列在 `devDependencies`。应先修正依赖归属，再裁剪，不能直接以生产安装替换并宣称完成。

后续修改镜像内容时，必须提供：

- 裁剪前后的依赖清单与镜像大小，确认不包含 Electron、测试工具、开发缓存、用户数据或凭据。
- 对实际保留的原生模块与系统工具说明用途；不能因开启数据库扩展而隐式要求 Xpod 容器具备 C++ 构建环境。
- 无宿主机源码 / `node_modules` 挂载时，Web 静态资源、Components.js 及运行时动态模块加载正常的证据。
- 同一 digest 的 Cloud / Local / Standalone 完整矩阵结果。Pod 读写、API Key 生命周期、模型读取、真实 Chat 和会话恢复分别报告；端口可达或空模型列表不能代替它们。

文档记录不代表依赖裁剪或发布验收已经完成；发布仍遵循 [发布流程](RELEASE.md)。
