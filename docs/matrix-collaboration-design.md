# Matrix 多智能体协作设计与验收契约

更新：2026-09-26。**本文描述目标契约；分布式能力尚未实现或验收通过。**
当前单 Pod adapter 的行为单列在文末，历史测试不作为目标能力证明。
决定来源见 [决策登记册](matrix-collaboration-decisions.md)，Pod 提交与迁移约束见
[存储契约](matrix-pod-storage-portability.md)。

## 产品与存储边界

实现 Matrix 的分布式房间、事件验证和同步语义，将各参与者的数据持久化到其 Pod。
一个逻辑房间可以跨部署、跨 Pod；同一个事件在副本间保留同一身份。共享 Pod 可以是部署
组合中的一种情况，不是协作半径的上限，也不能作为排除 federation 的理由。

Matrix 的复制单位原本是参与房间的 homeserver，一个 homeserver 可服务多个用户。
Xpod 的协议服务与参与者 Pod 的具体对应关系必须明确，不能假设每个 Pod 天然就是一个
拥有域名和签名密钥的 homeserver。服务处理协议，Pod 保存持久事实；二者职责分开。

消息、房间状态、同步/投递进度、事务记录及必要执行凭证都在 Pod。SQL journal 是旧实现的
待移除依赖。本地缓存、队列和查询索引只能是可重建状态，丢失后不能重置尝试预算、复活终态
任务或破坏历史请求的去重语义。数据归属不依赖是否有浏览器或浏览器缓存。

## 协议事件与 Pod 资源地址

| 概念 | 契约 |
| --- | --- |
| room_id / event_id | 稳定的 Matrix 协议身份，跨副本保持不变 |
| 协议事件 | 按 room version 保存及验证内容、前驱、授权链、hash/signature 等事实 |
| Pod 中的 Message URI | 某份持久消息资源的地址，可随目的 Pod 不同而不同，不是浏览器缓存 |
| Solid Chat 表示 | 用 models 表达消息、作者、正文、父关系及回复等共享语义；不替代完整协议事件 |
| event_id 查找 | 必须可定位对应事件；可由 schema、资源寻址或派生索引实现，不要求单独的映射表 |

对于当前讨论的 [room version 11](https://spec.matrix.org/v1.18/rooms/v11/#event-ids)，
event_id 是事件 reference hash 的协议编码；不能用随机字符串或 Pod URI hash 冒充。
资源地址构造不得反过来改变事件身份。复制原事件时不重写其已签名内容和事件关系；
Solid 关系的投影需与原始协议事实区分，并保持跨副本可追溯。

持久事件应保留验证及恢复需要的材料：room version、sender、type/state_key、content、
origin_server_ts、prev_events、auth_events、hashes、signatures，以及适用的 redaction 语义。
具体模型及原始事件载荷的组织由 models 设计；Xpod 不另造共享 schema，不手工复制序列化规则。

普通 Solid Chat 写入不是已经验证的 Matrix PDU。将其接入房间时，必须由获授权的协议服务
生成或关联一次合法事件，并持久记录导入去重；不能反复扫描就反复签发新事件。

## 协议处理责任

遵循 [Server–Server API](https://spec.matrix.org/v1.18/server-server-api/) 及所选 room version：

- 明确服务发现、server name、签名身份、密钥获取/轮换与服务器请求认证。
- 接收后校验事件结构、签名/hash、授权链、前驱及房间约束；缺失依赖按协议获取，不能
  因消息正文已写入 Pod 就当作已接受事件。
- 按事件图和 room version 解析房间状态；本地到达时间、journal 序号或简单最后写入不能
  替代 state resolution。power levels、成员及历史可见性遵守协议，不采用创建者永久独占管理。
- 定义重复/乱序到达、缺失事件补取、历史回填、redaction 与服务器交易重放的行为。
- 房间协议状态与本地处理状态分开：已接收、已验证、待补依赖、已接受、已投递不能混为一项。

协议范围不得仅凭“底层使用 Pod”而删去。客户端功能支持仍需逐项列明，本文不把 E2EE、
原生登录等尚未验证能力宣称为已支持，也不让它们掩盖 federation 的实现缺口。

## 三层同步与持久提交

| 层次 | 责任 | 持久记录与确认边界 |
| --- | --- | --- |
| 协议服务之间 | 发送/接收事件、验证、去重、补依赖和历史回填 | 服务器交易及事件处理记录；返回成功前必须达到可恢复的持久点 |
| 接收服务到参与者 Pod | 按房间及历史可见性确定接收资格，写入各自 Pod | 目的 Pod 的投递状态、事件引用、重试进度；部分成功不得标为全部完成 |
| Pod 到客户端 | 提供授权范围内的 timeline/state 增量与分页 | Pod 内发布状态及不透明客户端 token；不是服务器交易确认 |

同一部署内部投递可以使用本地传输适配，但必须走相同的事件验证、接收和落盘契约。
传输去重、event_id 去重、客户端 txnId 去重和执行去重分别定义，不能用同一个 key 代替。

接收待处理数据及投递状态也必须明确归属的 Pod；若接收时还不能写入最终参与者 Pod，
需定义受控的 Pod 内接收区及其权限/保留策略。具体归属是实现待办，不能偷放到唯一的本地 SQL
状态中，也不能在无持久恢复依据时向远端确认成功。

跨 Pod 不要求原子同时写入。A 已持久化、B 暂不可达时，持久保留 B 的待投递状态；恢复后
同事件身份补发，A 不重复产生消息或执行。目的资格变更和历史可见性必须参与补发判定。

Pod 内提交采用存储契约定义的可恢复意图、正文、发布和完成阶段。条件写的作用域是 HTTP
文档，不是其中的一个消息片段。未知写入结果先核验原操作，不直接重新生成事件。

## 客户端同步与 journal

journal 服务于本 Pod 的发布与增量读取，不承担全部分布式协议状态。客户端 token 可以表达
本地发布位置，不能当作房间全局顺序或远端投递确认。无全局序号也必须保证晚到事件不漏、
分页稳定、查询量有界、授权状态变化可见及崩溃后可恢复。

断开客户端重连只需携带其 token；服务端所需持久事实在 Pod。清空本地派生索引不得静默
跳过事件，位置空间重建需明确版本/epoch 和重同步行为。已有事件 ID 集合本身不提供有界
变更发现，不能用无限增长的 token 代替这一设计。

## 身份与授权

必须分别映射 Matrix 用户/设备、WebID、协议服务器签名身份、参与者 Pod、Agent 和 executor。
一个服务可托管多个用户/Pod，Pod 迁移不自动改变用户或房间协议身份。

- 用户访问自己的 Pod 使用其自身权限；不会因为加入房间就获得其他参与者 Pod 的写权限。
- 协议服务用明确获授的能力写目的 Pod，不借其他用户存量 owner 密钥。远端事件的 sender
  不是接收服务可以重放的 Solid 凭据。
- Matrix 事件授权验证其房间合法性，Solid ACL 限定存储访问，两者都必须满足各自契约。
- Agent 执行另需当前执行授权、有效触发和工具权限；有效 Matrix 事件不是执行授权的替代品。
- 跨请求 allow/deny 缓存在当前修复阶段停用，仅保留请求内复用；普通 PUT/PATCH 撤权后，
  后续请求不得命中旧判定。在途请求语义单独验收。

分布式传播存在延迟。新鲜读取本 Pod 不等于已知未收到的远端撤权。新的外部副作用需要
执行归属方可确认的授权/租约；无法确认时的暂停和恢复规则必须明确，不能宣称全网即时撤权。

## Agent 执行归属与恢复

消息复制与执行调度是不同操作。逻辑触发至少关联稳定 room_id、触发 event_id、目标 Agent
和执行用途；不得按各副本的 thread/message URI 生成彼此独立的任务身份。

必须为逻辑执行指定归属方及承载控制事实的 Pod，定义授权、claim、接替、尝试预算及终态。
其他 Pod 复制执行事件不获得执行权。多实例接替要服从同一控制事实，不能依靠互不共享的
Redis 租约或“各自看到 pending”决定执行；没有可验证接替授权时不得自行抢占。

Delivery、Run、RunStep 继续使用共享模型。需区分消息向某 Pod 的投递与向 Agent 的工作交付，
由 schema 明确表达，不把二者混用。模型及 attempt 语义先在 models 定义，结果发布为合法
Matrix 事件后再复制到有资格的参与者 Pod。

执行至少一次；工具以稳定逻辑操作 ID 幂等。副本数量不能变成独立执行数量，但这不承诺
故障期间外部副作用恰好一次。以下中断均需恢复：

| 中断点 | 要求 |
| --- | --- |
| claim 后、Run/attempt 落盘前 | 持久控制记录可对账，不永久 pending，也不重置预算 |
| 结果被接受、正文未持久化 | 保留可恢复载荷或安全接替规则，不能只用 hash 锁死任务 |
| 正文已写、发布/完成未确认 | 补齐原事件和终态，不能重新生成独立输出 |
| 结果已发布、远端未收到 | 从投递记录补发，不能重新运行 Agent |
| 本地队列/缓存丢失 | 从对应 Pod 重建，已完成/失败任务不复活 |

## 迁移与当前实现现状

现有 adapter 只能在同一已注册 Pod 内工作，使用本地成员/创建者策略、SQL journal、
Redis 或内存 wake 队列。它尚未提供这里要求的跨部署事件验证、状态解析与持久分发。
`/v1/agent-wakes/{claim,renew,complete,fail}` 是现有执行接口，不是 Federation API。

当前 fresh 标记覆盖 agent-wakes 上下文，但普通 Matrix 路径仍可能用跨请求缓存；不能将其
登记为上述全局授权修复已完成。全历史扫描及共享 SQL/Redis 依赖也仅是待替换现状。

迁移遵循存储契约：Pod 内保留原事务到原 ID/时间/内容的记录，区分新旧 token 空间，停旧写者，
在有界回滚阶段后移除 SQL journal。旧房间的随机事件 ID、缺失的签名/授权链和禁用 federation
不能通过改一个开关变成有效的 room v11 历史；需明确保留历史兼容面或导入新房间的流程，
不能伪造旧事件验证材料。分布式目标成立不意味着现有旧数据已经满足它。

## 验收门禁

现有 [样例](examples/matrix-collaboration.md) 和 [历史验收](matrix-collaboration-acceptance.md)
只证明原单身份、单 Pod 的确定性协作路径。新目标至少要求：

| 场景 | 必须证明 |
| --- | --- |
| 两个独立部署、身份与 Pod | 加入同一逻辑房间，事件复制后 room_id/event_id 不变，数据实际落各自 Pod |
| 同部署多个参与者 Pod | 不误发给无资格参与者；不因多份存储而重复向远端广播或启动执行 |
| 协议合法性 | 真实签名/hash/授权链验证，错误事件被拒绝；并发分支按 room version 得到一致状态 |
| 传输故障 | 断网、重复、乱序、响应丢失、部分目的 Pod 写入失败后可恢复；补取缺失依赖 |
| 权限 | 用户无需对方 Pod 写权限；接收能力不越界；leave/ban/历史可见性/撤权按契约处理 |
| Agent | 同一事件多份副本只有一个逻辑执行归属；重复交付、接替和队列重建不另起独立任务 |
| Pod 自足 | 禁用 SQL journal、清空本地派生状态后，事务、投递、同步和执行事实可从 Pod 恢复 |
| 性能 | 100/1,000/10,000 条历史下增量/空轮询/续租成本有界，测请求数与尾延迟 |
| 迁移 | 保留旧引用/重放结果；新旧协议房间和位置空间明确区分，回滚不丢新写入 |

必须保留实际版本、端点、身份/Pod 标识和可复查证据；两个 mock handler 互调、单 Pod 的
两个 runtime 或旧测试通过数均不能替代上述验收。
