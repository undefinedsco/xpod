# Xpod AFS

AFS owns the directory client, workcopy, search and mount client. CSS storage and authenticated server transport adapters stay in the service. Authentication uses the public CLI client; AFS has no second credential store.

Run `node scripts/check-afs-package.cjs` from the repository to build the public library in an isolated temporary workspace. This installs only declared AFS build/runtime dependencies, consumes the already built public CLI client payload, copies the canonical shared Bun type and Components generator configuration as explicit inputs, and uses `packages/xpod-afs/build.bun.lock`. It does not install or build the root service dependency graph. Use `--update-lock` only when declared build dependencies change. Receipts, input hashes and Node/Bun external ESM/CJS consumers are recorded under `.test-data/afs-module-split-20261011`; the temporary workspace is removed after closure.

The standalone library gate checks `tsconfig.client.json` (client and its producer) and invokes the existing `scripts/build-client.ts`. Platform capability packaging remains `scripts/build-package.ts --target <platform-arch> --out <directory> --native-evidence <zip> --native-pins <json>`, with the existing strict native admission and source equality. It requires genuine admitted native material and preserved original license/source provenance. The public notice build-tool/materials entries are consumed with byte inventory, source authority and client payload verification; the full isolated native platform packaging profile remains separate follow-up work; this library gate does not claim helper execution, mounting, publication or a complete platform release.

Pass `--cli-package <package-directory>` to validate an external public CLI payload; the default is the current workspace package. The package must export `./client`, `./build-tools` and `./producer-materials` and supply their actual dist/type payloads. All copied bytes are inventoried. Actual Node/Bun consumers call both public ESM and CJS notice tools on a real Bun build metafile. This is a controlled producer fixture, not native/material legal acceptance. `--check-pack-types` additionally checks the complete package producer public tooling contract.

Full isolated capability packing still needs a declared public producer material closure: CLI client payload/types, its original notices and generated-prefix provenance, public client build metafile plus reconstructible source authority, root-owned Xpod LICENSE, AFS original notice supplements, shared Components/Bun declarations, and the exact Git-bound native source/central gate plus genuine ZIP/pins. `build-package.ts` resolves the public client, tools and producer-materials exports. It no longer reads the CLI sibling source tree or its internal generated/metafile paths. The preserved source archive and inventory carry the declared public source authority, including dirty/unknown state; they do not grant immutable release acceptance. The staged runtime client advertises only its retained `./client` export, while the complete original manifest is preserved as provenance. A full isolated platform profile still requires the exact repository Git/native input closure consumed by native-material.py. These materials must retain upstream authority and original bytes; synthetic Git or a copied collector cannot stand in for them.

`check-producer-materials.ts` executes actual inventory rejection regressions for missing/hash-changed/duplicate/traversing/symlink/unlisted/source-inventory/client-payload/source-authority/directory fields. Public material source snapshot SHA and dirty state are preserved; no clean release identity is inferred.

Native installed tests may explicitly receive `XPOD_AFS_TEST_CLI_PACKAGE` while validating an external public CLI/tool payload before its commit is integrated; this is a test input, not product configuration, and can be omitted after the public package is available locally. `XPOD_AFS_TEST_ARCHIVE` still requires an actual capability archive with matching genuine native/source admission. The source-archive relation negatives use the shared public async `verifyProducerSourceArchive` verifier; exact membership, bytes and hashes are required in addition to the outer archive hash.

The module source inventory includes the shared `types/bun` declarations and `scripts/check-afs-package.cjs` library rebuild recipe, as well as the canonical `accept.py`/`supervise.py` source and actual `tools/agentfs-pod` inputs used by native material admission. A library rebuild runs that recipe with an explicitly supplied public CLI package whose client/tools/materials bytes match the preserved provenance. A complete capability pack also needs the genuine matching native ZIP/pins and Git objects required by the existing gate. The source directory or root lock alone is not that authority; do not initialize a synthetic Git history to satisfy admission. No complete platform rebuild is claimed until that real input closure has been tested.

Material validation repeats the same complete inventory and client payload checks after the shared async archive verifier, then returns hashes from that fixed declared snapshot. Packaging checks copied client/source archive/inventory bytes against those bindings. Regression cases mutate real copied material during the async verification boundary; they do not mock the public parser.
